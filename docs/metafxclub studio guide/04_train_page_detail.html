Flow Step 3 · Training

Train โมเดล RL อย่างมีวินัย

บทนี้อธิบายหน้า Train: เลือก dataset, ตั้งค่าหลักของ PPO, อ่าน log ระหว่าง train และรู้ว่าไฟล์ output แต่ละตัวเอาไปใช้ทำอะไรต่อ

เป้าหมาย ขั้นตอนใช้งาน ไฟล์ที่ต้องใช้ ค่าหลัก Suggested Steps กล่อง Advanced Reward Settings Action Profile เพิ่ม Action ใหม่ Confidence Filter Advanced PPO อ่าน Log ส่งต่อ Validation

Training คืออะไรใน flow นี้

Input

ใช้ dataset ที่ผ่าน Quality Check

ควรใช้ CSV ที่ timestamp ใช้ได้, feature ไม่เสีย, correlation ไม่หนักเกิน, และถ้าจะ deploy ควรมี .params.json คู่กัน

Learn

ให้ agent ฝึกจาก state → action → reward

agent เห็น feature window และสถานะ position แล้วเลือก action: Hold, Buy, Sell หรือ Close

Not Done

Train สำเร็จยังไม่แปลว่าใช้ได้

หลัง train ต้องผ่าน Backtest และ Walk-Forward ก่อนคิดเรื่อง export/deploy

ขั้นตอน Train ใน Dashboard

เวลาใช้สอน user ให้เริ่มจาก flow ตรงนี้ก่อน เพื่อให้เห็นว่าหน้า Train ต้องเดินจาก dataset ที่ผ่าน Quality Check ไปเป็น model artifact อย่างไร หลังจากนั้นค่อยลงรายละเอียดว่าไฟล์ output, Train %, window size, max hold และ PPO settings แต่ละตัวคืออะไร

1
Dataset

เลือก CSV ที่ผ่าน Step 2 แล้ว

เลือกไฟล์จากหน้า Train หรือใช้ไฟล์ที่ Regime Check ส่งมาให้ เช่น training_data_usdjpy_h4_dataset_from_2020-03-01.csv

2
Params

เช็ค .params.json

ถ้า dataset ไม่มี sidecar ให้กด Attach .params เฉพาะเมื่อมั่นใจว่าเป็น params ของ dataset ชุดเดียวกัน

3
Settings

ตั้งค่าหลักก่อน

ใช้ PPO, reward realized, reward profile Balanced, train pct 85, window 10, max hold 30, และตั้งชื่อโมเดลให้ชัด

4
Run

กด Start Training

ระบบจะรัน rl_train.py, split แบบ time-based, normalize จาก train stats เท่านั้น, train, save model และ quick test บน eval/test

5
Review

อ่านผลก่อน Validation

Train log ที่ไม่มี error ไม่พอ ต้องดู reward trend, PPO health metrics, quick test และ artifact ที่สร้างครบหรือไม่

ไฟล์ที่ Train ใช้และสร้างออกมา

ในหน้า Train ค่า Model Name จะกลายเป็นชื่อโฟลเดอร์และชื่อไฟล์ของโมเดล เช่นตั้งชื่อ rl_usdjpy_h4_v1 แล้วกด Start Training สำเร็จ ระบบจะสร้างไฟล์หลักไว้ใต้ project root ที่ artifacts/models/rl_usdjpy_h4_v1/

กลุ่มไฟล์ Path / ชื่อไฟล์ที่ได้ ใช้ทำอะไร

จำ path แบบสั้น: งาน train ใหม่จะอยู่ใน artifacts/models/<model>/ ส่วนไฟล์โมเดลเก่าที่เคยอยู่หน้า root เช่น <model>.zip, <model>_norm.csv หรือ <model>_best/best_model.zip ระบบยังพยายามค้นหาให้เพื่อรองรับงานเก่า แต่เวลาสอน user ให้ยึดโครงสร้างใหม่เป็นหลัก

ค่าหลักในหน้า Train

ค่า ความหมาย คำแนะนำเริ่มต้น
Algorithm ชนิด RL algorithm ที่ใช้ train ใช้ PPO (recommended) ก่อน เพราะเป็นค่าหลักของระบบนี้
Reward Mode วิธีให้คะแนน agent ใช้ realized เพราะเน้น reward จากการปิด trade และ net P/L จริง
Reward Profile preset นิสัยการเรียนรู้ของ reward ตอน train เริ่มที่ Balanced; เปลี่ยน profile แล้วต้อง train model ใหม่
Action Profile ชุดคำสั่งที่ model เลือกได้ เช่น Basic 4 หรือ Manage 6 เริ่มที่ Basic 4; ถ้าเลือก Manage 6 output dim จะเปลี่ยนและต้อง train/export ใหม่
Training Steps จำนวน step ที่ agent ได้ฝึก; ปุ่ม Use suggested เป็นค่าประมาณจากจำนวน train bars เลข suggested อาจซ้ำที่ 200000 ได้ เพราะมี minimum floor และการปัดเลข ดูรายละเอียดหัวข้อ Suggested Steps
Window Size จำนวน bars ย้อนหลังที่ agent เห็นใน state เริ่ม 10; window ใหญ่ขึ้นทำให้ observation ใหญ่ขึ้นและ train หนักขึ้น
Max Hold จำนวน bars สูงสุดที่ถือ position ก่อน force close เริ่ม 30; ควรสัมพันธ์กับ timeframe และ style ของระบบ
Train % แบ่งข้อมูลแบบ time-based: ต้นไฟล์เป็น train, ท้ายไฟล์เป็น eval/test ใช้ 85 ได้สำหรับเริ่มต้น และห้ามคิดว่าเป็น random split
MC Eval Runs Monte Carlo หลัง quick eval: shuffle ลำดับ trade ดูการกระจาย DD + สุ่มตัด trade ดู profit retention (เกณฑ์แบบ SQX) — วัดความ robust ของ recipe ตั้งแต่ model เกิด ใช้ 1000 (default); ใส่ 0 เพื่อปิด · ผลบันทึกใน <model>.train.json · DD ที่ได้เป็นโลกอุดมคติ (env ไม่มี costs) — ใช้คัดกรอง recipe เท่านั้น ทุนจริงดูจาก MC ฝั่ง Backtest
MC Skip % สัดส่วน trade ที่สุ่มตัดทิ้งต่อรอบ skip-MC — ถ้าตัดแล้วกำไรพัง แปลว่า edge กระจุกอยู่ไม่กี่ไม้ (เปราะ) ใช้ 10 (default) · verdict ผ่านเมื่อ retention ≥ 70% และ P(flip) < 5%
Model Name ชื่อ artifact ที่จะถูกสร้าง เช่น rl_usdjpy_h4_v1 ใส่ symbol/timeframe/version ให้ชัด และระวังชื่อซ้ำเพราะจะ overwrite

Suggested Steps คิดจากอะไร

ค่า Suggested steps ในหน้า Train และ Full Pipeline ไม่ใช่ค่าที่โมเดลคำนวณจากความยากของตลาดโดยตรง และไม่ใช่สัญญาณว่า dataset สองไฟล์เหมือนกัน แต่เป็น heuristic สำหรับตั้งจำนวน training steps เริ่มต้นจากจำนวนแท่งที่ใช้ train จริง

ทำไมบางทีเห็น 200,000 ตลอด? ถ้า dataset หลังหัก Train % และ Window Size มี train bars อยู่ในช่วงประมาณ 5,000–30,000 ระบบจะใช้ minimum floor ที่ 200,000 steps และปัดเป็นช่วงละ 50,000 ดังนั้นหลาย dataset ขนาดใกล้กัน โดยเฉพาะ H4 หลายปี อาจได้ suggested steps เท่ากันได้ตามปกติ

สูตรโดยย่อ

โปรแกรมเริ่มจากคำนวณ train bars ประมาณนี้: effective_train_bars = int(total_rows × train_pct) - window_size จากนั้นเลือกจำนวน pass และ minimum steps ตามขนาดข้อมูล

Effective train bars Target passes Minimum steps ผลที่พบบ่อย
< 5,000 ประมาณ 30 passes 100,000 ไฟล์เล็กมากยังได้ steps ขั้นต่ำเพื่อให้ PPO มีรอบเรียนพอ
5,000–30,000 ประมาณ 12 passes 200,000 เป็นช่วงที่มักเห็น suggested = 200,000 ซ้ำกัน
30,000–100,000 ประมาณ 8 passes 400,000 dataset ใหญ่ขึ้นจึงเพิ่ม baseline steps
>= 100,000 ประมาณ 5 passes 600,000 ข้อมูลใหญ่มาก ใช้ pass ต่อข้อมูลน้อยลงแต่ยังมี floor สูง

หลังคำนวณแล้วระบบจะปัดเลขเป็น block ละ 50,000 steps เพื่อให้ค่าที่แนะนำอ่านง่ายและไม่แกว่งเล็กน้อยทุกครั้งที่จำนวน row เปลี่ยนนิดเดียว

วิธีใช้ที่ถูก: ใช้ suggested steps เป็นจุดเริ่มต้นเท่านั้น จากนั้นดู ep_rew_mean, approx_kl, clip_fraction, backtest และ walk-forward ประกอบ ถ้า reward แบนยาวหรือ OOS แย่ลง การเพิ่ม steps อย่างเดียวอาจทำให้ overfit มากขึ้น

3 กล่อง Advanced ในหน้า Train

กล่องในรูปเป็นส่วนที่เปลี่ยน “วิธีที่ agent เรียนรู้” และ “สิ่งที่ agent ทำได้” ไม่ใช่แค่หน้าตา UI ดังนั้นควรปรับแบบมีสมมติฐาน ทดลองทีละชุด และเทียบผลด้วย Backtest/Walk-Forward หลังจาก train ใหม่ทุกครั้ง

กล่องในหน้า Train ควบคุมอะไร ส่งผลกับไฟล์/ขั้นตอนไหน ควรแตะเมื่อไหร่
Advanced PPO Settings hyperparameters ของ PPO เช่น learning rate, rollout, batch, discount และ critic loss ส่งเข้า rl_train.py แล้วบันทึกใน <model>.train.json เมื่อ metric เช่น approx_kl, clip_fraction, value_loss บอกว่า train ไม่เสถียร
Advanced Reward Settings น้ำหนัก reward ที่ใช้สอน agent เช่น ให้รางวัลกำไรจริง, ลงโทษ overtrade, time decay, give-back ส่งเป็น reward_profile, reward_overrides หรือ reward_profile_json ตอน train เมื่ออยากเปลี่ยนนิสัยของ agent เช่น ให้เข้าไม้น้อยลง, ลด drawdown, ถือ trend นานขึ้น หรือถือสั้นลง
Action Profile & Parameters ชุด action ที่โมเดล output ได้ เช่น 4 action พื้นฐาน หรือเพิ่ม action จัดการ SL เปลี่ยน action_space, output dimension ของ PPO, backtest, export และ EA live เมื่ออยากให้โมเดลไม่ได้แค่ Buy/Sell/Close แต่บริหาร position เช่น Move SL to BE หรือ Trail SL
ถ้าเปลี่ยน Reward Settings หรือ Action Profile โมเดลเดิมจะไม่เปลี่ยนนิสัยย้อนหลัง ต้อง train โมเดลใหม่เสมอ โดยเฉพาะ Action Profile เพราะจำนวน output ของ network เปลี่ยนได้จริง

Reward Profile คืออะไร

Reward Profile คือชุด preset ที่ปรับน้ำหนักใน reward function ของ TradingEnv เพื่อเปลี่ยนนิสัยการเรียนรู้ของ agent ระหว่าง train เท่านั้น หลัง train เสร็จ Backtest/Live/EA จะใช้ policy ที่โมเดลเรียนมา ไม่ได้เปิดอ่าน reward profile อีก

Profile นิสัยที่สอน เหมาะกับการลองเมื่อ
Balanced สูตรเดิมของระบบ เน้น net P/L ตอนปิดไม้ พร้อม penalty กัน overtrade เริ่มต้นทุกครั้ง หรือใช้เป็น baseline เทียบ profile อื่น
Anti Overtrade เพิ่มต้นทุน reward ตอนเปิดไม้ใหม่ เช่น trade_penalty จากค่าปกติประมาณ 0.005 เป็นประมาณ 0.010 เพื่อบังคับให้ agent เปิด trade เฉพาะเมื่อสัญญาณคุ้มกับต้นทุนมากขึ้น ใน env ตอน train ระบบถือได้ทีละ position อยู่แล้ว ดังนั้น profile นี้ไม่ได้แก้ปัญหาเปิดหลายออเดอร์พร้อมกัน แต่แก้พฤติกรรมเปิด-ปิดถี่, เข้าไม้พร่ำเพรื่อ หรือรีบเข้าใหม่ทันทีหลังปิดไม้ ใช้เมื่อจำนวน trade สูงมาก แต่ PF/return ไม่ดี, equity แกว่งจาก churn, หรือ backtest แสดงว่า model เข้าออกตลาดบ่อยเกินไป
Low Drawdown ลงโทษ loss, give-back และการถือผิดทางแรงขึ้น equity แกว่งแรง หรือ max drawdown สูงเกินรับได้
Trend Follower ผ่อน time decay และให้ direction hint ระหว่างถือ position มากขึ้น ตลาดเป็น trend และอยากให้ model อดทนถือไม้ได้นานขึ้น
Scalper เน้นปิดเร็ว time decay เริ่มไว และให้ bonus กับ win ที่เล็กกว่า อยากทดลองระบบถือสั้น หรือ timeframe ต่ำกว่า H4

Advanced Reward Settings

ถ้าเปิด Show Reward Sliders ในหน้า Train ค่าที่เห็นคือ parameter ย่อยของ reward profile ปัจจุบัน ผู้ใช้สามารถเลื่อนเฉพาะค่าที่อยากทดลองได้ ระบบจะส่งค่าที่ต่างจาก preset เข้า rl_train.py --reward_overrides และบันทึกทั้ง overrides กับ config สุดท้ายไว้ใน artifacts/models/<model>/<model>.train.json

ส่วนในกล่อง Reward หน้าที่ ผลที่เกิดขึ้นตอนกด Train
Show Reward Sliders เปิด/ปิดแผง slider ของ reward parameters ถ้าไม่เปิด ระบบยังใช้ reward profile ที่เลือกไว้ตามปกติ ไม่มี override เพิ่ม
Reset to profile ดึงค่าทุก slider กลับไปเป็น default ของ Reward Profile ปัจจุบัน ล้างการทดลองที่เลื่อนไว้ เพื่อให้ train รอบใหม่กลับมาเทียบกับ preset ได้สะอาด
Load JSON โหลด reward recipe จากไฟล์ metafxclub.reward_profile.v1 ตั้งค่า base profile, overrides และสูตร developer formula ถ้ามีใน JSON
Save JSON บันทึก base profile + slider overrides + formula เป็น recipe เหมาะกับการเก็บสูตรที่ทดลองแล้วไว้ใช้ซ้ำหรือส่งให้เครื่องอื่น
Reward JSON: none/path บอกว่าตอนนี้มี JSON recipe โหลดอยู่หรือไม่ ถ้ามี path แปลว่าตอน train จะส่ง recipe นั้นเข้า rl_train.py ด้วย
Developer Mode เปิดโหมดใช้ custom reward formula แบบ safe expression สูตรนี้มีผลเฉพาะตอน train และถูกบันทึกไว้ใน train metadata เพื่อ audit ย้อนหลัง

ค่าบน slider เป็น reward shaping ไม่ใช่ risk setting ของ broker: มันบอก agent ว่า behavior แบบไหนควรได้คะแนนมาก/น้อยระหว่างเรียน แต่หลัง train แล้ว Backtest/Live/EA จะใช้ policy ที่เรียนมา ไม่ได้เปิดอ่าน slider เหล่านี้เพื่อคำนวณ order ใหม่

Reward Profile JSON

ปุ่ม Save JSON จะบันทึก base profile และ slider overrides เป็นไฟล์ recipe ส่วนปุ่ม Load JSON จะโหลด recipe กลับมา ตั้งค่า profile และเลื่อน slider ให้ตรงกับไฟล์ เหมาะสำหรับเก็บสูตร reward ที่อยากใช้ซ้ำหรือแชร์ให้เครื่องอื่น 

{
  "schema": "metafxclub.reward_profile.v1",
  "name": "anti_overtrade_example",
  "base_profile": "anti_overtrade",
  "overrides": {
    "trade_penalty": 0.012,
    "unrealized_scale": 0.04
  }
}

ถ้าใช้ CLI สามารถส่งไฟล์ตรง ๆ ได้ด้วย --reward_profile_json reward_profile_configs\anti_overtrade_example.json. ถ้าส่งทั้ง JSON และ --reward_overrides ค่า override จาก CLI จะทับค่าจาก JSON

Developer Mode: Custom Formula

Developer Mode เปิดให้เขียนสูตร reward เป็น safe expression ได้เอง สูตรนี้ใช้แทน reward shaping แบบ realized ใน TradingEnv แต่ยังใช้ execution logic เดิม เช่น spread, commission, max hold และ action space เดิม 

(unrealized_delta * unrealized_scale)
- (trade_penalty if just_opened else 0)
+ (trade_closed_pnl * close_pnl_mult if trade_closed else 0)

เพื่อความปลอดภัย ระบบไม่อนุญาต import, assignment, loop, attribute access หรือการเรียก function อิสระ ใช้ได้เฉพาะ expression, if/else, comparison, boolean logic และ helper ที่ whitelist ไว้: abs, min, max, round, sqrt, log, exp, tanh, clip, sign

ตัวแปรที่ใช้ได้ เช่น trade_closed_pnl, unrealized_delta, just_opened, is_idle, giveback, time_decay_active, bars_in_position, max_hold_bars และ reward params ทุกตัว เช่น trade_penalty, close_pnl_mult, profit_bonus, unrealized_scale

Custom Formula เป็น developer feature: สูตรที่ดูฉลาดใน train อาจ exploit reward ได้ง่าย ต้องเทียบด้วย Backtest, Walk-Forward และดูจำนวน trade/drawdown ทุกครั้ง
กลุ่มค่า ปรับแล้วเกิดอะไร ข้อควรระวัง
close_pnl_mult, loss_penalty_mult เปลี่ยนน้ำหนักกำไร/ขาดทุนตอนปิดไม้ สูงเกินไปอาจทำให้ reward แกว่งและ train ไม่เสถียร
trade_penalty, idle_penalty ควบคุมว่าการเปิดไม้หรือการไม่ทำอะไรแพงแค่ไหน trade penalty สูงมากอาจทำให้ agent ไม่กล้าเปิด order
unrealized_scale, giveback_* ปรับแรงจูงใจระหว่างถือไม้และโทษเมื่อคืนกำไรลอยตัว unrealized สูงเกินไปอาจทำให้ agent เล่น dense reward แทนกำไรจริง
time_decay_start, time_decay_penalty กำหนดว่าเริ่มลงโทษการถือไม้นานเมื่อไรและแรงแค่ไหน ควรดูคู่กับ Max Hold และ timeframe ของ dataset
Reward slider ความหมายละเอียด ถ้าเพิ่มค่านี้
Close PnL Mult ตัวคูณกำไร/ขาดทุนสุทธิเมื่อปิด position เป็นน้ำหนักหลักของ reward แบบ realized โมเดลสนใจกำไรจริงตอนปิดไม้มากขึ้น แต่ reward อาจแกว่งแรงขึ้น
Loss Penalty Mult ตัวคูณเพิ่มเฉพาะไม้ที่ปิดแล้วขาดทุน โมเดลกลัว loss มากขึ้น อาจลด drawdown แต่ก็อาจปิดไม้เร็วหรือไม่กล้าเข้า
Bonus Threshold / Profit Bonus กำไรต้องเกิน threshold เท่าไรจึงได้ bonus และ bonus นั้นมีน้ำหนักเท่าไร บังคับให้ agent มองหา win ที่มีระยะพอ ไม่ใช่กำไรจิ๋ว ๆ ตลอดเวลา
Unrealized Scale direction hint ระหว่างถือ position จากกำไร/ขาดทุนลอยตัว โมเดลตอบสนองระหว่างถือไม้มากขึ้น แต่สูงเกินไปอาจเรียนจากกำไรลอยตัวแทน P/L ตอนปิดจริง
Giveback Trigger/Fraction/Penalty ระบบลงโทษเมื่อกำไรลอยตัวเคยขึ้นไปแล้วคืนกำไรกลับมามากเกิน โมเดลอาจเรียนรู้ให้ปกป้องกำไรเร็วขึ้น แต่ถ้าแรงเกินไปอาจตัด trend เร็ว
Trade Penalty ต้นทุน reward ตอนเปิด trade ใหม่ ลด overtrade และ churn; ถ้าสูงเกินไป model อาจ Hold มากเกินจนแทบไม่เปิด order
Idle Penalty โทษเล็ก ๆ ตอน agent Hold ว่างโดยไม่มี position บีบให้ agent หาโอกาสมากขึ้น แต่ถ้าสูงไปอาจบังคับเข้าไม้ทั้งที่ edge ไม่พอ
Time Decay Start/Penalty เริ่มลงโทษหลังถือ position เกินสัดส่วนของ Max Hold และลงโทษต่อ bar เท่าไร โมเดลถือไม้นานน้อยลง เหมาะกับ scalping/mean-reversion มากกว่า trend following
ห้ามเทียบผลข้าม profile จาก quick eval อย่างเดียว ให้ใช้ dataset เดียวกัน, train pct เดียวกัน, steps ใกล้กัน แล้วค่อยเทียบผ่าน Backtest และ Walk-Forward

Action Profile: model ทำอะไรได้บ้าง

Action Profile คือชุดคำสั่งที่ PPO output ออกมาได้ ไม่ใช่แค่ label ในหน้าจอ เพราะจำนวน action จะกลายเป็น output dimension ของ policy network โดยตรง ดังนั้นเปลี่ยน Action Profile แล้วต้อง train model ใหม่ และตอน export EA ต้องใช้ profile เดียวกัน

ในเชิงเทคนิค TradingEnv จะสร้าง spaces.Discrete(N) ตามจำนวน action ใน profile นั้น เช่น Basic 4 คือ output 4 ช่อง แต่ Manage 6 คือ output 6 ช่อง ถ้าเอาโมเดล 4 action ไปใช้กับ EA/Backtest ที่คาดหวัง 6 action ระบบจะตีความ action ผิดหรือ reject ด้วย action profile mismatch

Basic 4

Hold / Buy / Sell / Close

เป็นค่า default เดิมของระบบ เหมาะกับ baseline test และโมเดลเก่าที่มี output 4 ช่อง

Manage 6

เพิ่ม Move SL to BE และ Trail SL by ATR

model จะเลือก action จัดการ stop ได้เอง ได้แก่ move_sl_breakeven และ trail_sl_atr โดย backtest/export/EA จะอ่าน schema เดียวกันจาก train metadata

Action ID Basic 4 Manage 6 ความหมายตอน train/backtest
0 Hold Hold ไม่ทำอะไรใน bar นี้ ถ้ามี position ก็ถือไม้ต่อ
1 Buy Buy เปิด long เมื่อยังไม่มี position หรือเมื่อ execution layer อนุญาต
2 Sell Sell เปิด short เมื่อยังไม่มี position หรือเมื่อ execution layer อนุญาต
3 Close Close ปิด position ปัจจุบันเพื่อรับ realized P/L
4 - Move SL to BE ถ้ามีกำไรลอยตัวเกินเงื่อนไข ให้เลื่อน SL มาที่ราคาเข้า
5 - Trail SL by ATR ถ้ามีกำไรลอยตัวเกินเงื่อนไข ให้เลื่อน SL ตามราคาโดยใช้ระยะ ATR

Action Parameters ในกล่องนี้

slider ในการ์ด Action Profile & Parameters ไม่ได้เปลี่ยน feature input แต่เปลี่ยนเงื่อนไขของ action จัดการไม้และ reward cost ที่ agent เห็นระหว่าง train ค่าเหล่านี้จะถูกบันทึกใน <model>.train.json และตอน export จะถูกแปลงเป็น macro ในไฟล์ config ของ EA เช่น RL_ACTION_TRAIL_ATR_MULT เพื่อให้ EA live ใช้กติกาเดียวกับโมเดล

Action Parameter ใช้ทำอะไร ข้อควรระวัง
breakeven_min_profit กำไรลอยตัวขั้นต่ำก่อนย้าย SL ไปที่ราคาเข้า ต่ำเกินไปอาจโดน BE บ่อยและตัดโอกาส trend
trail_atr_period, trail_atr_mult กำหนดระยะ trailing stop จาก ATR proxy mult ต่ำเกินไปจะ trail ชิด ราคาแกว่งนิดเดียวก็ปิด
trail_min_profit กำไรลอยตัวขั้นต่ำก่อนเริ่ม trail ควรสอดคล้องกับ timeframe และความผันผวนของ symbol
management_action_penalty, invalid_action_penalty ต้นทุน reward สำหรับ action จัดการไม้ เพื่อไม่ให้ agent spam action สูงเกินไป agent อาจไม่ยอมใช้ trailing แม้ควรใช้
ชื่อใน UI key ใน JSON default / ช่วง คำอธิบายละเอียด
BE Min Profit breakeven_min_profit 0.0010 / 0.0..0.05 หน่วยเป็นสัดส่วนกำไรเทียบราคาเข้า เช่น 0.0010 = 0.10%. ถ้า long และกำไรลอยตัวถึง threshold จะตั้ง SL อย่างน้อยที่ราคาเข้า; ถ้า short จะตั้ง SL ไม่สูงกว่าราคาเข้า
Trail ATR Period trail_atr_period 14 / 2..100 bars จำนวนแท่งย้อนหลังที่ใช้คำนวณ ATR proxy สำหรับ trailing action. ค่าน้อยตอบสนองเร็วแต่ไวต่อ noise; ค่าสูง smooth กว่าแต่ trailing ช้าลง
Trail ATR Mult trail_atr_mult 2.00 / 0.1..10.0 ระยะ trailing = ATR proxy x multiplier. long จะใช้ candidate ประมาณ price - ATR*mult; short จะใช้ candidate ประมาณ price + ATR*mult
Trail Min Profit trail_min_profit 0.0010 / 0.0..0.05 กำไรลอยตัวขั้นต่ำก่อน action trail จะมีผลจริง ถ้ายังไม่ถึง threshold agent กด trail แล้วจะถือว่า action ใช้งานไม่ได้และโดน invalid penalty
Manage Penalty management_action_penalty 0.00020 / 0.0..0.01 reward cost เล็ก ๆ เมื่อ management action ใช้งานได้จริง ใช้กันไม่ให้ agent กด move/trail ซ้ำ ๆ ทุก bar โดยไม่มีเหตุผล
Invalid Action Penalty invalid_action_penalty 0.00100 / 0.0..0.02 reward cost เมื่อ management action ใช้ไม่ได้ เช่น ไม่มี position, กำไรยังไม่ถึง threshold หรือ SL ใหม่ไม่ได้ดีขึ้นจาก SL เดิม
Buy/Sell ทำงานแยกฝั่ง: Move SL to BE และ Trail SL by ATR รองรับทั้งฝั่ง long และ short. Long จะเลื่อน SL ขึ้นเพื่อปกป้องกำไร ส่วน short จะเลื่อน SL ลงตามราคา โดยระบบจะไม่เลื่อน SL ถอยหลังไปทางที่แย่กว่าเดิม

Developer Action JSON / DSL

ปุ่ม Load JSON และ Save JSON ในการ์ด Action Profile & Parameters ใช้เก็บ recipe แบบจำกัดไว้แชร์หรือใช้ซ้ำ ตัว JSON ยังไม่อนุญาตให้เขียน Python/MQL5 เอง แต่เลือกได้เฉพาะ primitive ที่ระบบรองรับ เพื่อให้ flow dataset → train → backtest → export → EA live map action ตรงกันทุกชั้น 

{
  "schema": "metafxclub.action_profile.v1",
  "name": "manage_6_example",
  "base_profile": "manage_6",
  "params": {
    "trail_atr_mult": 2.5,
    "trail_min_profit": 0.0015
  }
}
ปุ่มในกล่อง Action หน้าที่ ควรใช้เมื่อไหร่
Reset คืน Action Profile และ parameter กลับค่า default ของ profile ที่เลือก หลังทดลอง slider แล้วอยากกลับ baseline ก่อน train รอบใหม่
Load JSON โหลด action recipe ที่จำกัด primitive/action params ตาม schema เมื่อมีสูตร action parameter ที่ต้องการใช้ซ้ำหรือเทียบกับเครื่องอื่น
Save JSON บันทึก profile + params ปัจจุบันเป็นไฟล์ recipe หลังเจอค่า BE/trailing ที่อยากเก็บไว้ใช้ train รอบต่อไป
Action JSON: none/path แสดงว่ากำลังใช้ recipe จากไฟล์หรือปรับจาก UI โดยตรง ใช้เช็คก่อน train ว่ารอบนี้อิง recipe ไหนอยู่
Action Profile เป็นส่วนหนึ่งของ architecture ไม่ใช่ filter หลัง train: model ที่ train ด้วย Basic 4 ใช้กับ EA ที่คาดหวัง Manage 6 ไม่ได้ เพราะจำนวน output และความหมายของ action ไม่ตรงกัน
ถ้าต้องการให้ Codex เพิ่มหรือปรับ action ใหม่ ให้ใช้ prompt ใน docs/codex_custom_action_prompts.md เพื่อบังคับให้แก้ครบทั้ง train, backtest, fine-tune, walk-forward, full pipeline, export และ EA live

วิธีเพิ่ม Action Profile / Custom Action ใหม่

การเพิ่ม action ไม่เหมือนการเพิ่ม input ทั่วไป เพราะ action คือสิ่งที่โมเดลเลือกออกมาโดยตรง ถ้าเปลี่ยนจำนวน action หรือเปลี่ยนความหมายของ action จะกระทบตั้งแต่ตอน train ไปจนถึง EA live ดังนั้นต้องออกแบบก่อน แล้วค่อยแก้ครบทั้ง flow dataset → train → backtest → fine-tune → walk-forward → full pipeline → export → EA live

1. ออกแบบ action ให้ชัดก่อนแก้โค้ด

สิ่งที่ต้องกำหนด ตัวอย่าง ทำไมต้องกำหนด
ชื่อ action / ชื่อ profile partial_close, scale_in, Manage 8 ใช้เป็นชื่อใน metadata, JSON recipe, GUI, backtest log และ EA config
ใช้กับ position แบบไหน buy, sell, both, หรือใช้ได้เฉพาะตอนมี position ป้องกัน logic ผิดฝั่ง เช่น trail short ด้วยสูตร long หรือแก้ SL ผิดทิศ
เงื่อนไขที่ action ใช้ได้ ต้องมีกำไรลอยตัวเกิน 0.0010, ต้องมี SL เดิม, ต้องถือมาอย่างน้อย N bars ให้ train/backtest/EA ตัดสิน invalid action เหมือนกัน
ถ้า action ใช้ไม่ได้ให้ทำอะไร ignore, treat as Hold, หรือหัก invalid_action_penalty เป็นส่วนหนึ่งของ reward shaping ถ้าไม่กำหนด agent อาจ spam action ที่ใช้ไม่ได้
parameter ที่ user ปรับได้ trail_atr_period, trail_atr_mult, partial_close_pct ต้องรู้ว่าจะเก็บใน JSON, train metadata, export config และ EA input อย่างไร
ผลข้างเคียงต่อ order แก้ SL, ปิดบางส่วน, เปิดเพิ่ม, reverse position ยิ่งกระทบ order มาก ยิ่งต้อง validate ใน MT5/Strategy Tester อย่างเข้ม

2. แยกก่อนว่าเพิ่มแค่ profile หรือเพิ่ม action ใหม่จริง

ง่ายกว่า

เปลี่ยนชุด action เดิม / เพิ่ม preset ใหม่

ถ้าใช้ primitive เดิม เช่น hold, buy, sell, close, move_sl_breakeven, trail_sl_atr แต่ต้องการ profile ใหม่หรือค่า default ใหม่ ให้แก้หลัก ๆ ที่ ACTION_PROFILES ใน action_profiles.py

ต้องแก้ครบ flow

เพิ่ม action primitive ใหม่

ถ้า action ไม่เคยมีมาก่อน เช่น partial_close, scale_in, reverse_position ต้องเพิ่มทั้งความหมายใน env, backtest, export และ EA live เพราะโมเดลจะมี output ช่องใหม่จริง

3. ไฟล์ที่ต้องแก้ตามระดับของงาน

กรณี ไฟล์ที่ต้องแก้ รายละเอียด
เพิ่ม profile จาก action เดิม action_profiles.py เพิ่ม/แก้ ACTION_PROFILES, ค่า default params, label และ description. GUI จะดึง ACTION_PROFILE_LABELS ไปแสดงอัตโนมัติ

เพิ่ม action ใหม่จริง action_profiles.py, trading_env.py, backtest_live.py, rl_train.py, rl_finetune.py, rl_walkforward.py, rl_app.py, export_to_onnx.py, mt5_files\MQL5\Experts\ML_RL_Trader_template.mq5 เพิ่ม primitive, action id, execution logic ตอน train, execution logic ตอน backtest, UI/CLI plumbing, metadata, export config และ EA live branch

4. Flow หลังเพิ่ม action/profile

1
Implement

แก้โค้ดให้ train/backtest/export/EA เข้าใจ action เดียวกัน

ห้ามแก้เฉพาะหน้า GUI เพราะ action ต้องมีความหมายเดียวกันใน TradingEnv, backtest_live.py และ EA template

2
Retrain

Train โมเดลใหม่

เปลี่ยน action space แล้ว model เก่าใช้ต่อไม่ได้ เพราะ output dimension หรือ action meaning เปลี่ยน แม้จำนวน action เท่าเดิมแต่ความหมายเปลี่ยน ก็ต้อง train ใหม่เพื่อไม่ให้ policy ตีความผิด

3
Validate

Backtest + Walk-Forward ด้วย profile เดียวกัน

Backtest ควรอ่าน profile จาก model metadata หรือระบุ profile/params เดียวกับตอน train แล้วใช้ Walk-Forward เพื่อดูว่า action ใหม่ช่วยจริงหรือแค่ fit กับช่วงหนึ่งของข้อมูล

4
Export

Export EA ใหม่

EA ต้องรู้ action IDs, จำนวน output และ parameter ของ action ใหม่ ดังนั้นต้อง export package ใหม่จากโมเดลที่ train ด้วย action profile นั้น

5
MT5

Compile/Test ใน MetaEditor และ MT5 Strategy Tester

หลังแก้ ML_RL_Trader_template.mq5 หรือ export EA ใหม่ ต้อง compile ใน MetaEditor และทดสอบใน MT5 ว่า action ใหม่ไม่เปิด order ผิดฝั่ง ไม่แก้ SL ผิดทิศ และ log ไม่มี mismatch

5. ใช้ prompt เพื่อบังคับให้ Codex แก้ครบ

ถ้าผู้ใช้งานต้องการเพิ่ม action ใหม่เอง ให้เริ่มจาก prompt ใน docs/codex_custom_action_prompts.md เพราะ prompt นั้นบังคับให้ Codex อ่านและแก้ครบทั้ง action_profiles.py, trading_env.py, backtest_live.py, rl_train.py, rl_finetune.py, rl_walkforward.py, rl_app.py, export_to_onnx.py และ ML_RL_Trader_template.mq5

อย่าเพิ่ม action ใหม่เฉพาะใน JSON หรือเฉพาะใน GUI ถ้า train/backtest/EA ยังไม่มี logic รองรับ เพราะโมเดลจะ output action id ที่บางชั้นไม่รู้จัก ทำให้ backtest เพี้ยนหรือ EA live ไม่ทำงานตรงกับที่ train มา

Confidence Filter ใช้ตอน Train ไหม

ตอน train และ quick eval ของ rl_train.py ไม่ได้ใช้ Confidence Threshold. ระบบให้ PPO เลือก action ด้วย model.predict(obs, deterministic=True) แล้วส่ง action นั้นเข้า environment ตรง ๆ ดังนั้นมุมมองตอน train จะใกล้กับ Backtest แบบ Pure Agent, Confidence = 0 และ Max Positions = 1

Train / Quick eval

ไม่มี gate จาก confidence

agent เรียนจาก reward ว่า Hold, Buy, Sell หรือ Close แล้วผลดีหรือเสีย ไม่ได้เรียนกติกาว่า probability ต้องมากกว่า 0.85 ถึงจะเปิด order

Backtest / Live

ค่อยใช้เป็น execution gate

หลัง train แล้วจึงค่อยใช้ confidence threshold เพื่อกรอง Buy/Sell ที่ไม่มั่นใจ แต่ต้อง calibrate จาก validation ของแต่ละโมเดล ไม่ใช่ fix 0.85 ทุกตัว

สถานการณ์ ควรตั้งค่าอย่างไร เหตุผล
เช็คว่า policy ที่ train มามี edge ไหม Pure Agent, Confidence = 0, Max Positions = 1 ใกล้กับ environment ตอน train มากที่สุด และใช้เทียบกับ quick eval ได้ตรงกว่า
เตรียมใช้ live หรือ EA sweep 0, 0.3, 0.5, 0.7, 0.85, 0.9 confidence ของ PPO ไม่ได้แปลว่าโอกาสชนะจริงเสมอ ต้องหา threshold ที่ดีจาก OOS/WF
filter ทำให้ PF แย่ลง ลด threshold หรือปิด filter สำหรับโมเดลนั้น แปลว่า confidence ยังไม่ calibrate กับ trade quality อย่าฝืนใช้ค่า default
ข้อควรจำ: ไม่ต้องกำหนด confidence filter ตอน train. ให้ train policy ก่อน จากนั้นใช้ Backtest/Analyze เพื่อ calibrate threshold สำหรับการส่ง order จริง

Advanced PPO Settings ควรแตะเมื่อไหร่

สำหรับ user ใหม่ ให้ใช้ค่า default ก่อน แล้วค่อยกลับมาแก้เมื่ออ่าน log/backtest แล้วมีเหตุผล

กล่องนี้ถูกซ่อนไว้หลัง Show Advanced เพราะเป็นค่าระดับ optimization ของ PPO ไม่ใช่ strategy rule โดยตรง ถ้าปรับผิดอาจทำให้ train ดูเหมือนเร็วขึ้นแต่ OOS แย่ลง ทุกค่าจะถูกส่งเป็น argument เข้า rl_train.py และบันทึกไว้ใน <model>.train.json เพื่อย้อนดูได้ว่าโมเดลนี้ train ด้วย hyperparameter ชุดไหน

ค่า ใช้แก้อาการอะไร แนวทาง
learning_rate policy แกว่ง, KL/clip สูง, reward พังเร็ว ลดจาก 3e-4 เป็น 1e-4
clip_range ควบคุมไม่ให้ PPO เปลี่ยน policy แรงเกินในแต่ละ update เริ่ม 0.2; ไม่ควรปรับถ้ายังไม่อ่าน PPO metrics เป็น
ent_coef agent ไม่ explore หรือ action ซ้ำเกินไป เพิ่มเล็กน้อยเมื่อ exploration หาย แต่ต้อง backtest ยืนยัน
n_steps, batch_size, n_epochs ควบคุม rollout และ optimization batch_size ต้องไม่เกิน n_steps
gamma, gae_lambda, vf_coef discount, advantage smoothing และ critic/value loss ใช้ default ก่อน เว้นแต่มีเหตุผลจาก metric หรือ experiment

ช่องที่อยู่ใน Advanced PPO

ช่องใน UI default ความหมาย อ่านอาการจาก log
Learning Rate 3e-4 ความแรงของการอัปเดต policy/critic ในแต่ละ optimization step ถ้า approx_kl หรือ clip_fraction สูงและ reward พังเร็ว ให้ลดเป็น 1e-4
Clip Range 0.2 กรอบที่ PPO ใช้จำกัดไม่ให้ policy ใหม่ต่างจาก policy เก่าแรงเกินไป ถ้า policy แกว่งมาก ใช้ 0.1 เพื่อ conservative ขึ้น; ถ้าเรียนช้ามากอาจลอง 0.3
Entropy Coef 0.01 แรงจูงใจให้ agent explore action หลากหลาย ไม่รีบล็อกเป็น action เดียว ถ้า action กระจุกมากหรือ Hold/Close ซ้ำผิดปกติ ลองเพิ่ม เช่น 0.05
n_steps 2048 จำนวน step ใน rollout buffer ก่อนนำไป update policy เพิ่มเป็น 4096 มักนิ่งขึ้นแต่ช้าขึ้น; ลดเป็น 1024 เร็วขึ้นแต่ noisy กว่า
n_epochs 10 จำนวนรอบที่นำ rollout เดิมกลับมา optimize ซ้ำ มากเกินไปอาจ overfit กับ rollout สั้น ๆ; fast preset ใช้ 5
batch_size 64 ขนาด minibatch ที่ใช้ optimize จาก rollout ต้องไม่เกิน n_steps; ใหญ่ขึ้นนิ่งขึ้นแต่กิน memory/เวลาเพิ่ม
gamma 0.99 discount factor ว่าให้ความสำคัญกับ reward ในอนาคตแค่ไหน ค่าใกล้ 1 เหมาะกับการถือหลาย bar; ลดลงจะทำให้ agent สนใจผลระยะสั้นมากขึ้น
gae_lambda 0.95 ตัว smooth advantage ระหว่าง bias/variance ของสัญญาณเรียนรู้ ใช้ default ก่อน ปรับเมื่อเข้าใจความสัมพันธ์ของ reward variance แล้ว
vf_coef 0.5 น้ำหนัก loss ของ critic/value function เทียบกับ policy loss ถ้า value loss แปลกมาก อาจทดลองช่วง 0.25..1.0 แต่ต้องวัด OOS

Quick Presets

Preset ค่าหลักที่เปลี่ยน ใช้เมื่อไหร่
Default lr=3e-4, clip=0.2, ent=0.01, n_steps=2048 baseline สำหรับเริ่ม train และใช้เทียบกับ preset อื่น
Stable lr=1e-4, clip=0.1, n_steps=4096, batch=128 เมื่อ train แกว่ง, KL/clip สูง, reward collapse หรืออยากลดความรุนแรงของ policy update
Fast lr=5e-4, clip=0.3, n_steps=1024, n_epochs=5 ใช้ทดลองเร็ว ๆ เพื่อดูทิศทาง ไม่ควรใช้สรุป production โดยไม่ผ่าน OOS/WF
Explorer ent_coef=0.05 ที่เหลือใกล้ Default เมื่อ agent ติด action เดิมหรือ explore น้อยเกินไป
สอน user แบบง่าย: Advanced PPO ไม่ใช่ที่สำหรับเดาสุ่ม ถ้า train ไม่ดีให้กลับไปดู data, regime, feature และ reward trend ก่อน แล้วค่อยปรับ hyperparameters

อ่าน Log ระหว่าง Train

สิ่งที่เห็น แปลว่าอะไร ควรทำอะไร
ep_rew_mean ค่อย ๆ ดีขึ้น agent เริ่มได้ reward จาก environment Go ปล่อยจนจบ แล้วไป Backtest
reward collapse หรือแกว่งแรง อาจ learning rate สูง, data noisy, หรือ reward ถูก exploit Review ลด LR หรือกลับไปดู data/feature
approx_kl หรือ clip_fraction สูงผิดปกติ policy เปลี่ยนแรงเกินไป Tune ลด learning rate หรือใช้ Stable preset
มี NaN/error หรือ train data too small ข้อมูลหรือ setting ไม่พร้อม Stop กลับไป Quality Check

ส่งต่อไป Validation

เมื่อ train จบและ artifact สร้างครบ ให้ไปหน้า Backtest เพื่อพิสูจน์ด้วยผลลัพธ์เทรดจริงใน simulation

ก่อนออกจากหน้า Train ควรมี ถ้าไม่มี
Model artifact artifacts/models/<model>/<model>.zip train ยังไม่จบหรือ error
Normalization stats artifacts/models/<model>/<model>_norm.csv อย่า backtest/export เพราะ input scale อาจไม่ตรง
Params parity artifacts/models/<model>/<model>.params.json ถ้ามี sidecar ต้นทาง ยัง backtest ได้ แต่ก่อน deploy ควรแก้ parity ให้ครบ
ประโยคสอน user: การ train คือการสร้างผู้สมัครโมเดล ยังไม่ใช่การอนุมัติให้ใช้งานจริง ผู้สมัครต้องผ่าน Backtest และ Walk-Forward ก่อน
