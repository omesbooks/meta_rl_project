Fine-tune — ปรับ model เดิมด้วยข้อมูลใหม่

บทนี้อธิบายหน้า Fine-tune: โหลด model ที่ train ไว้แล้วมา train ต่อด้วย data ใหม่ โดยผสม data เก่าไว้ ~30% เพื่อกันลืมของเดิม ใช้ steps น้อยกว่าและเร็วกว่า train scratch มาก พร้อมเกณฑ์ว่าเคสไหนควร fine-tune และเคสไหนต้องกลับไป train ใหม่ทั้งตัว

เป้าหมาย Fine-tune vs Retrain เลือกเมื่อไหร่ ขั้นตอนใช้งาน ค่าในหน้า Fine-tune Base Model Contract ไฟล์ที่ใช้ Quick Eval ตัดสินใจ Gotchas

Fine-tune ต่างจาก Train from Scratch อย่างไร

จุดสำคัญคือ fine-tune ไม่ได้ train ด้วย "data ใหม่อย่างเดียว" เพราะแบบนั้นจะเกิด catastrophic forgetting — network ปรับ weights ไปหาข้อมูลใหม่จนลืม pattern เก่าที่เคยใช้ได้ ระบบจึงใช้โหมด mixed เป็นค่าเริ่มต้น: สุ่ม data เก่ามาผสม ~30% รวมกับ data ใหม่ทั้งหมด ~70% แล้วเรียงตาม timestamp ก่อน train

Train Scratch

เริ่ม weights ใหม่หมด

สุ่ม weights ใหม่ แล้วเรียนจาก data ทั้งหมด (เก่า+ใหม่) ~200k steps ด้วย learning rate ปกติ (3e-4)

ได้ model ที่สะอาดที่สุด เปลี่ยนอะไรก็ได้ทั้ง feature, window, action profile, reward แลกกับเวลาและ compute ที่มากกว่า

Fine-tune (mixed)

ต่อยอดจาก weights เดิม

โหลด model เดิม ปรับ learning rate ลงเหลือ 1e-4 แล้ว train ต่อ ~50k steps บน mix เก่า 30% / ใหม่ 70%

เร็วและถูกกว่า แต่ต้องคง "สัญญา" ของ model เดิมไว้ทุกอย่าง: feature เดิม, window เดิม, action profile เดิม, reward เดิม

อยากเห็นภาพว่า weights เปลี่ยนต่างกันยังไง: เปิด explainer 09_train_vs_finetune.html เป็น interactive เปรียบเทียบ Train Scratch / Pure Fine-tune / Smart Fine-tune (Mixed) ทีละ cycle — เห็นชัดว่าทำไม pure fine-tune ถึงลืมของเก่า และทำไม mixed ถึงจำได้ บทนี้จะไม่เล่าซ้ำ แต่เน้นการใช้งานหน้า Fine-tune จริง

เคสไหน Fine-tune เคสไหนต้อง Retrain

กฎง่ายที่สุด: fine-tune ใช้ได้เฉพาะตอนที่ "ข้อมูลใหม่ขึ้น แต่โจทย์เดิม" ถ้าโจทย์เปลี่ยน (feature เปลี่ยน, action เปลี่ยน, reward เปลี่ยน) ต้อง train scratch เท่านั้น

สถานการณ์ วิธีที่ถูก เหตุผล
เก็บ data ใหม่มาเพิ่มอีก 2-3 เดือน โครงสร้างเหมือนเดิม Fine-tune เคสตรงตัวที่สุด — ให้ model รู้จักช่วงตลาดล่าสุดโดยไม่ทิ้งของเดิม
ตลาดเปลี่ยน regime แบบอ่อน ๆ (volatility ขยับ, trend เปลี่ยนทิศ) Fine-tune weights เดิมยังใกล้คำตอบ แค่ปรับจูนด้วย data ช่วงใหม่ก็พอ
ตลาดเปลี่ยนโครงสร้างแรง (เหตุการณ์ระดับ COVID/Brexit) หรือ backtest ตัวเดิมพังยาว ลองทั้งสอง fine-tune อาจดึงไม่ไหว — รัน fine-tune เทียบกับ train scratch แล้วให้ Backtest ตัดสิน
เพิ่ม/ลบ/เปลี่ยน feature columns หรือเปลี่ยน window size Retrain observation shape ไม่ตรงกับ model เดิม ระบบจะ error ตั้งแต่ตรวจ contract
เปลี่ยน action profile (เช่นจาก 3 actions เป็น 5 actions) Retrain เป็นไปไม่ได้ทาง fine-tune — output layer ของ network มีจำนวนช่องคงที่ตาม profile เดิม
เปลี่ยน reward mode / reward profile / reward formula Retrain fine-tune อ่าน reward settings จาก metadata ของ base model เสมอ เปลี่ยนกลางทางไม่ได้
เปลี่ยน symbol หรือ timeframe (เช่น USDJPY H4 → EURUSD H1) Retrain ถือเป็นโจทย์ใหม่ทั้งตัว การกระจายของ data ต่างกันมากเกินกว่าจะจูน
จำง่าย ๆ: Fine-tune = "data ใหม่ โจทย์เดิม" · Retrain = "โจทย์เปลี่ยน" — ถ้าไม่แน่ใจว่าโจทย์เปลี่ยนไหม ให้ดูว่า Backtest/Quality Check บอกอะไร และถ้าลังเลระหว่างสองทาง ให้ทำทั้งคู่แล้วเทียบผลบน data ชุดเดียวกัน

ขั้นตอน Fine-tune ใน Dashboard

หน้า Fine-tune ตั้งใจให้เรียบที่สุด: เลือก 3 อย่าง (base model, old CSV, new CSV) ตั้งชื่อใหม่ แล้วกดปุ่มเดียว ที่เหลือระบบดึงจาก metadata ของ base model ให้หมด

1
Base

เลือก Base Model

เลือก model เดิมจาก dropdown Existing Model — ควรเป็น model ที่เคยผ่าน Backtest แล้ว เพราะ fine-tune ต่อยอดจากของเดิม ถ้าฐานแย่ ผลลัพธ์ก็แย่ตาม

2
Data

เลือก Old CSV และ New CSV

Old Data CSV = ไฟล์ที่ใช้ train base model (ไว้สุ่มมาผสมกันลืม) และ New Data CSV = data ช่วงใหม่ที่อยากให้ model เรียนเพิ่ม ทั้งสองไฟล์ต้องมี feature columns ครบตามที่ base model ใช้

3
Settings

ตั้ง Mode, Mix Ratio, Learning Rate, Steps, ชื่อใหม่

ค่าเริ่มต้น Mode = mixed, Mix Ratio = 0.3, LR = 1e-4, Steps = 50000 ใช้ได้เลยเกือบทุกเคส ที่สำคัญคือ New Model Name — ตั้งชื่อใหม่เสมอ (เช่น rl_uj_h4_v2) อย่าใช้ชื่อเดียวกับ base เพราะจะเสีย model เดิมที่ไว้เทียบ/rollback

4
Run

กด Start Fine-tuning แล้วอ่าน log

ระบบจะพิมพ์ base contract (features, window, action profile) ให้ตรวจก่อน train จากนั้น train ~50k steps (ราว 10 นาที) จบแล้วรัน quick eval บน data ใหม่ให้อัตโนมัติ

5
Gate

Backtest + Walk-Forward ก่อนใช้จริง

quick eval เป็นแค่ sanity check — ตัวตัดสินจริงคือหน้า Backtest (เทียบ base vs fine-tuned บน data ชุดเดียวกัน) และ Walk-Forward ถ้าตัวใหม่ไม่ชนะตัวเก่า ให้ใช้ตัวเก่าต่อ

ค่าในหน้า Fine-tune

ค่า ความหมาย คำแนะนำเริ่มต้น
Base Model (Existing Model) model เดิมที่จะโหลด weights มา train ต่อ เลือกตัวที่ผ่าน Backtest แล้ว — ระบบอ่าน window, action profile, reward จาก metadata ของตัวนี้ทั้งหมด และมีบรรทัด hint ใต้ dropdown สรุปสูตรที่จะสืบทอดให้เห็นทันที (reward / action / window / max hold)
Mode mixed ผสมเก่า+ใหม่ตาม ratio · pure ใช้ data ใหม่ล้วน (Mix Ratio ไม่ถูกใช้) · replay ทบทวน data เก่าอย่างเดียว ใช้ mixed เกือบทุกเคส — pure เฉพาะเมื่อ regime เปลี่ยนจริงจนของเก่าเป็นพิษ, replay ไว้กู้ model ที่เริ่มเพี้ยน
Learning Rate ขนาดก้าวของการปรับ weights ต่อรอบ เริ่ม 1e-4 (ต่ำกว่า train scratch ~3 เท่า) — สูงไป = ลืมของเก่า (catastrophic forgetting), ถ้ายังลืมอยู่ลองลดเป็น 5e-5
Old Data CSV data ชุดเดิม (ที่เคยใช้ train base) — ระบบสุ่มบางส่วนมาผสมเพื่อกัน catastrophic forgetting ใช้ไฟล์เดียวกับตอน train base model เพื่อให้ "ความจำเก่า" ตรงของจริง
New Data CSV data ช่วงใหม่ที่อยากให้ model ปรับตัวเข้าหา — ถูกใช้ทั้งไฟล์ ควรเป็นช่วงเวลาต่อจาก old CSV จาก broker/collector เดียวกัน feature ครบชุดเดิม
Mix Ratio (old %) สัดส่วน data เก่าใน training mix เช่น 0.3 = เก่า 30% / ใหม่ 70% (ต้องอยู่ในช่วง 0 ถึงน้อยกว่า 1) เริ่ม 0.3; ถ้า regime ใหม่ต่างจากเดิมมากลองลดเป็น 0.2, ถ้ากลัวลืมของเดิมเพิ่มเป็น 0.4
Steps จำนวน timesteps ที่ train ต่อ เริ่ม 50000 (~1/4 ของ train scratch); data ใหม่เยอะมากค่อยขยับเป็น 100000
New Model Name ชื่อ model ใหม่ — ระบบสร้างโฟลเดอร์ artifacts/models/<name>/ แยกจาก base ตั้งชื่อแบบมี version เช่น rl_uj_h4_v2 อย่าทับชื่อ base model เดิม

หน้า GUI เรียก rl_finetune.py ให้เบื้องหลัง โดยค่าที่ไม่มีช่องให้กรอก จะใช้ default ของ CLI ซึ่งออกแบบมาสำหรับ fine-tune โดยเฉพาะ:

ค่า (CLI default) ค่าที่ใช้ ทำไม
Window / Max Hold / Ep Len ตาม base model อ่านจาก train_meta.json ของ base — เปลี่ยนไม่ได้เพราะผูกกับ observation shape
Reward mode / profile / formula ตาม base model เปลี่ยน reward กลางทาง = ย้ายเป้าหมายให้ policy เดิม ผลจะเพี้ยน จึงล็อกตาม base
PPO hyperparameters อื่น ๆ ตาม base model ติดมากับไฟล์ model ตอน PPO.load อยู่แล้ว (ยกเว้น LR ที่ตั้งใหม่ได้จากช่องในหน้า)
คำสั่งที่ GUI รันจริง: python rl_finetune.py <base> --old_csv <old> --new_csv <new> --mode mixed --mix_ratio 0.3 --lr 1e-4 --steps 50000 --name <new_name> — เหลือเฉพาะ --window/--max_hold/--ep_len ที่ override ได้จาก command line เท่านั้น (จงใจไม่มีช่องใน GUI เพราะเสี่ยง mismatch กับ base model)

Base Model Contract: อะไรถูกล็อกไว้บ้าง

ก่อน train ระบบจะโหลด base model ขึ้นมา probe แล้วตรวจ "สัญญา" 4 ข้อ ถ้าข้อไหนไม่ตรง จะหยุดพร้อม error ทันที ไม่ train ต่อให้เสียเวลา — ตารางนี้คือสิ่งที่ต้องเหมือน base model ทุกประการ:

สิ่งที่ล็อก ระบบตรวจอย่างไร ถ้าไม่ตรงจะเจอ
Feature columns อ่านรายชื่อ features จาก metadata ของ base แล้วเช็คว่า old/new CSV มีครบทุกคอลัมน์ ERROR: ... missing N base-model features พร้อมรายชื่อคอลัมน์ที่หาย
Window / Observation shape คำนวณ window × features + 3 เทียบกับ observation space จริงของ model ERROR: observation shape mismatch — ต้องกลับไปใช้ feature set/window เดิม
Action profile เทียบจำนวน actions ใน profile กับ output ของ network (action_space.n) ERROR: action profile has X actions but base model outputs Y
Reward settings ไม่มีช่องให้แก้ — ดึง reward mode/profile/formula จาก metadata ของ base มาใช้ตรง ๆ (ไม่ error เพราะแก้ไม่ได้ตั้งแต่แรก)
ทำไมเปลี่ยน action profile ทาง fine-tune ไม่ได้: output layer ของ neural network มีจำนวน neuron เท่ากับจำนวน actions ตอน train ครั้งแรก เช่น model 3 actions มีช่อง output 3 ช่อง — จะยัด profile 5 actions เข้าไปไม่ได้ เพราะโครงสร้าง network เปลี่ยนไม่ได้หลังสร้างแล้ว อยากได้ action ชุดใหม่ = train from scratch เท่านั้น ไม่มีทางลัด

นอกจาก contract แล้ว ระบบยังช่วยจัดการ data ให้อัตโนมัติ: ตัดคอลัมน์ leaky/target (future_*, forward_*, next_*, target) ทิ้ง, เรียงตาม timestamp, และ normalize features ด้วย สถิติของ base model (mean/std จาก norm.csv เดิม) — ไม่คำนวณใหม่ เพราะ weights เดิมถูก train บน scale นั้น ถ้าเปลี่ยน scale weights จะอ่าน input ผิดความหมายทันที

ไฟล์ที่ Fine-tune ใช้และสร้างออกมา

ไฟล์ / ค่า หน้าที่ หมายเหตุ
<base>.zip + train_meta.json ของ base input: weights ตั้งต้น + metadata ที่ใช้ resolve contract ถ้า metadata หาย ระบบพยายาม infer window จาก observation shape ให้ แต่ควรมีครบ
Old CSV / New CSV input: data สำหรับ mix (เก่า ~30% / ใหม่ทั้งไฟล์) จำนวนแถวเก่าที่สุ่ม = new_rows × ratio ÷ (1−ratio) ไม่เกินจำนวนแถวเก่าที่มีจริง
artifacts/models/<name>/<name>.zip output: model ใหม่หลัง fine-tune โผล่ใน dropdown ของหน้า Backtest / Walk-Forward / Export อัตโนมัติ
<name>_norm.csv สถิติ normalize ของ model ใหม่ copy มาจาก norm ของ base model (ต้องเป็นชุดเดียวกัน — ดู Gotchas)
<name>.params.json sidecar สำหรับ Export/EA (spread, lot, symbol settings) forward ต่อจาก base model เป็นอันดับแรก (ถ้าไม่มี ค่อย fallback ไป sidecar ของ new/old CSV)
train_meta.json ของ model ใหม่ บันทึกว่าเป็น fine-tune (fine_tune: true), ชื่อ base model, mix ratio, ช่วงเวลา data, quick eval stats ใช้ตามรอยได้เสมอว่า model ตัวนี้ต่อยอดมาจากตัวไหนด้วย data ชุดไหน

Quick Eval หลัง Fine-tune อ่านยังไง

พอ train จบ ระบบจะรัน model ใหม่บน data ใหม่ทั้งไฟล์ แบบ deterministic แล้วพิมพ์ block Quick eval on NEW data ใน log (return, trades, win rate ฯลฯ) พร้อมบันทึกลง train_meta.json — มีไว้ตอบคำถามเดียว: "model ปรับตัวเข้ากับ data ใหม่ได้จริงไหม" ยังไม่ใช่ผลที่เอาไปตัดสิน deploy

ข้อจำกัด 1

eval บน data ที่เพิ่งเรียน

data ใหม่ถูกใช้ train ไปแล้ว (70% ของ mix) — ผลนี้จึงเป็น in-sample ตัวเลขดูดีเกินจริงได้เสมอ

ข้อจำกัด 2

ไม่มี confidence filter / risk

quick eval ใช้ action ตรงจาก policy ไม่มี SL/TP ไม่มี filter — เทียบได้กับ Backtest แบบ Pure Agent, Confidence = 0 เท่านั้น

วิธีใช้ที่ถูก

ใช้เป็น sanity check

ถ้า quick eval ยังแย่ (return ติดลบหนัก, แทบไม่ trade) ไม่ต้องเสียเวลา Backtest — กลับไปดู data/mix ratio ก่อนเลย

ขั้นถัดไปที่ log แนะนำ: python backtest_live.py <name> <csv> --conf 0 --mode pure_agent — คือ baseline backtest แบบเดียวกับที่สอนไว้ในหน้า Backtest Detail (ใช้หน้า Backtest ใน GUI แทนก็ได้ ตั้งค่าให้ตรงกัน)

Decision: Fine-tune เสร็จแล้วทำอะไรต่อ

เกณฑ์ตัดสินไม่ใช่ "model ใหม่ดีไหม" แต่คือ "model ใหม่ชนะ base model ไหม" — รัน Backtest ทั้งสองตัวบน data ทดสอบชุดเดียวกัน setting เดียวกัน แล้วเทียบ:

สถานะ ความหมาย ตัดสินใจ
Go ตัวใหม่ชนะ base ชัดบน data ใหม่ (PF/return/DD ดีกว่า) และไม่แย่ลงบน data เก่า ไป Walk-Forward ต่อ ผ่านแล้วค่อยคิดเรื่อง Export แทนตัวเดิม
Review ดีขึ้นบน data ใหม่ แต่แย่ลงบน data เก่า (อาการเริ่มลืม) หรือผลใกล้เคียง base มาก ลองเพิ่ม mix ratio (0.4), ลด steps, หรือรัน train scratch มาเทียบเป็นตัวเลือกที่สาม
Stop แพ้ base model ทั้งสองช่วง หรือ quick eval พังตั้งแต่ต้น ใช้ base model ต่อไปก่อน แล้วสอบสวนว่า data ใหม่มีปัญหา (Quality Check) หรือ regime เปลี่ยนแรงจนต้อง retrain

Checklist ก่อนถือว่า fine-tune "ผ่าน" จริง:

  1. Backtest model ใหม่บน data ใหม่ (out-of-sample ถ้าแบ่งได้) — ต้องชนะ base
  2. Backtest model ใหม่บน data เก่า — ต้องไม่ทรุดหนักจาก base (เช็ค forgetting)
  3. Walk-Forward model ใหม่ — edge ต้องทนหลายช่วงเวลา ไม่ใช่ดีเฉพาะช่วงที่เพิ่งเรียน
  4. เก็บ base model ไว้เสมอจนกว่าตัวใหม่จะพิสูจน์ตัวเองครบทุกด่าน
ประโยคสอน user: Fine-tune คือการส่ง model ไปเรียนคอร์สเสริม ไม่ใช่การได้ปริญญาใหม่อัตโนมัติ — เรียนจบต้องสอบ (Backtest + Walk-Forward) เหมือนเดิมทุกครั้ง และถ้าสอบแพ้รุ่นพี่ (base model) ก็ยังไม่มีเหตุผลต้องเปลี่ยนตัว

Gotchas ที่เจอบ่อย

อาการ สาเหตุ ทางแก้
Error missing base-model features ตั้งแต่เริ่ม CSV ใหม่สร้างจาก feature set คนละชุดกับตอน train base (เช่น เปลี่ยน indicator ใน collector) สร้าง CSV ใหม่ด้วย pipeline/feature ชุดเดิมของ base — หรือถ้าตั้งใจเปลี่ยน feature จริง ให้ไป train scratch
Error observation shape mismatch window หรือจำนวน features ที่ resolve ได้ไม่ตรงกับ observation space ของ base model อย่า override window เอง ปล่อยให้ระบบอ่านจาก metadata; เช็คว่า CSV มีคอลัมน์ครบไม่ขาดไม่เกิน
Log ขึ้น base stats not found; recomputing norm.csv ของ base model หาย ระบบเลยคำนวณ mean/std ใหม่จาก data fine-tune อันตราย — scale input จะไม่ตรงกับที่ weights เดิมเคยเห็น ให้หา norm ของ base กลับมาก่อนแล้วรันใหม่
ผลดีบน data ใหม่ แต่พังบน data เก่า catastrophic forgetting — mix ratio ต่ำไป หรือ steps เยอะไปสำหรับ data ใหม่ที่มีน้อย เพิ่ม mix ratio เป็น 0.4, ลด steps, หรือใช้ old CSV ที่ยาวขึ้นให้มีตัวอย่างเก่าหลากหลายกว่าเดิม
Export แล้ว EA ใช้ค่า spread/lot ไม่ตรงกับ data ใหม่ params.json ถูก forward จาก base model เป็นอันดับแรก ไม่ได้อ่านจาก CSV ใหม่ เปิด <name>.params.json ตรวจก่อน Export ทุกครั้ง ถ้า broker/เงื่อนไขเปลี่ยนให้แก้ไฟล์นี้ให้ตรง
ตั้งชื่อใหม่ทับชื่อ base model ใช้ค่า default หรือพิมพ์ชื่อซ้ำโดยไม่ตั้งใจ model เดิมถูกเขียนทับ = เสียตัวเทียบและตัว rollback — ตั้งชื่อแบบ version (_v2, _ft1) เสมอ
Fine-tune ซ้ำหลายรอบต่อกันแล้วผลเพี้ยนขึ้นเรื่อย ๆ chain แบบ v1 → v2 → v3 สะสม drift ที่ละรอบ โดยเฉพาะถ้า old CSV ที่ใช้ผสมสั้นลงเรื่อย ๆ fine-tune ต่อเนื่องได้ 2-3 รอบพอ หลังจากนั้นควร train scratch ด้วย data ทั้งหมดสักครั้งเพื่อ reset ฐาน
สรุปใจความ: Fine-tune คือทางลัดที่ปลอดภัยเฉพาะเมื่อ "สัญญาเดิมครบ" — feature เดิม, window เดิม, action profile เดิม, norm เดิม, params ตรวจแล้ว ขาดข้อใดข้อหนึ่งเมื่อไหร่ ทางลัดจะกลายเป็นทางอ้อมที่แพงกว่า train ใหม่เสมอ
