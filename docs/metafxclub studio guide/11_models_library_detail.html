Flow Step · Model Library

Model Library — เปรียบเทียบและเลือก model อย่างมีหลักฐาน

บทนี้อธิบายหน้า Models: ตารางเปรียบเทียบทุก model กับผล backtest ล่าสุดของแต่ละตัว, ความหมายของแต่ละคอลัมน์ (รวมคอลัมน์ใหม่ Realism และ Params), equity curve viewer, ปุ่มต่าง ๆ, โครงสร้าง artifacts บนดิสก์ และหลักการเลือก model ไป deploy โดยไม่หลงกับ PF สวย ๆ ตัวเดียว

หน้านี้คืออะไร ขั้นตอนใช้งาน คอลัมน์ในตาราง คอลัมน์ Realism คอลัมน์ Params Equity Viewer + ปุ่ม Artifacts บนดิสก์ เลือก model ไป deploy Gotcha

หน้า Models คืออะไรใน flow นี้

หน้า Backtest ให้ผลทีละ model ทีละรอบ — แต่หน้า Models คือ "ศูนย์รวม": มันสแกนผล backtest ล่าสุดของทุก model ที่เคยรัน แล้ววางเทียบกันในตารางเดียว เพื่อให้ตอบคำถามสำคัญได้เร็ว: ตอนนี้มี model ไหนบ้าง ตัวไหนมีหลักฐานดีที่สุด และหลักฐานนั้นเชื่อได้แค่ไหน

Compare

Evidence

Trust

ไม่ใช่แค่ตัวเลข แต่บอกความน่าเชื่อด้วย

คอลัมน์ Realism บอกว่าผลนั้นพึ่งข้อมูล M1 จริงหรือพึ่งการเดา และคอลัมน์ Params บอกว่า config ฝั่ง MT5 ตรงกับตอน train ไหม

คอลัมน์ในตาราง Model Comparison ทีละตัว

คอลัมน์ ความหมาย วิธีอ่าน / ข้อควรระวัง
Model ชื่อ model (ชื่อเดียวกับโฟลเดอร์ artifacts/models/<name>/) ตั้งชื่อให้สื่อ symbol + timeframe + version เช่น rl_uj_h4_v3 จะเทียบง่ายมาก
Result source ที่มาของตัวเลขในแถวนั้น: live backtest = ผลจาก backtest แบบ live logic (SL/TP, risk, slippage), env backtest = ผลจาก backtest แบบ environment เดียวกับตอน train, model only = มีแค่ไฟล์ model ยังไม่เคย backtest เทียบข้าม source ตรง ๆ ไม่แฟร์ — env backtest มักดูดีกว่าเพราะไม่มี cost แบบ live ตัวที่จะ deploy ควรมีผลจาก live backtest เสมอ
Trades จำนวน trade ทั้งหมดใน trade log ล่าสุด ตัวเลขอื่นทุกตัวยืนอยู่บน sample size นี้ — trades น้อย (เช่น < 30) ทำให้ PF/Win rate เป็นแค่เรื่องบังเอิญได้ง่าย
Win rate สัดส่วน trade ที่กำไร (%) Win rate สูงแต่ avg loss ใหญ่ = ยังเจ๊งได้; ต้องอ่านคู่กับ PF เสมอ
PF (Profit Factor) กำไรรวมจาก trade ชนะ ÷ ขาดทุนรวมจาก trade แพ้ PF < 1 = ขาดทุนสุทธิ; inf = ไม่มี trade แพ้เลย ซึ่งมักแปลว่า trades น้อยเกินไป ไม่ใช่ model เทพ
Return ผลตอบแทนรวม (%) คำนวณจาก trade log (base equity 10,000) ตารางเรียงตามคอลัมน์นี้ — แต่ Return สูงสุด ≠ ตัวที่ควร deploy (ดู section เลือก model)
Max DD drawdown ลึกสุดของ equity curve (%) คือ "ราคาที่ต้องจ่าย" ระหว่างทาง — Return ดีแต่ DD เกินที่ใจรับได้ = ใช้จริงไม่รอด
Realism ⭐ ใหม่ ความน่าเชื่อของผล backtest ในแถวนั้น (intrabar SL/TP ตัดสินด้วยข้อมูลจริงหรือการเดา) สำคัญมากจนแยกไปอธิบายเต็ม ๆ ใน section ถัดไป
Chart yes = มีไฟล์ HTML chart แบบ interactive ให้เปิดดู ถ้า - ให้ไป generate จากหน้า Backtest ก่อน ถึงจะกด Open HTML chart ได้
Params สถานะ parameter parity ระหว่าง training pipeline กับ config ฝั่ง MT5 สามค่า: ✓ sidecar / ✓ embedded / — defaults — อธิบายเต็มใน section Params

คอลัมน์ Realism: ผลนี้ "จริง" แค่ไหน

Backtest บน H4 เดินทีละ bar แต่ราคาจริงวิ่งภายใน bar — ถ้าทั้ง SL และ TP อยู่ใน range ของ bar เดียวกัน (ambiguous bar) ระบบต้องเดาว่าโดนอะไรก่อน เว้นแต่จะมีข้อมูล M1 ให้ replay จริง (รายละเอียดใน Backtest Detail → Execution Realism) คอลัมน์ Realism สรุปเรื่องนี้ของ "ผลล่าสุดที่เก็บไว้" ให้เห็นในตารางเลย โดยอ่านจากไฟล์ <model>_live_bt.meta.json ของ backtest รอบนั้น

ค่าในคอลัมน์ แปลว่าอะไร ควรทำอะไร
M1 ✓ backtest รอบนั้นใช้ข้อมูล M1 จริง resolve เคส intrabar SL/TP — เคสกำกวมถูกตอบด้วยราคาระดับนาที ไม่ใช่สมมติฐาน เชื่อถือได้มากที่สุด ใช้เทียบ/ตัดสินใจได้เลย
ok ไม่มี ambiguity เลย (ไม่มี bar ไหนที่ SL+TP ตกใน bar เดียวกัน) — มักเกิดเมื่อ SL/TP กว้างเทียบ bar range หรือ exit ส่วนใหญ่มาจาก agent Close ใช้ได้เลย แม้ไม่มี M1 เพราะไม่มีอะไรต้องเดาตั้งแต่แรก
guess N% N% ของ SL/TP exits ถูกตัดสินด้วยการเดา (สมมติฐาน pessimistic/optimistic) — ยิ่ง N สูง ผลรวมยิ่งเชื่อไม่ได้ เพราะแค่เปลี่ยนสมมติฐาน ตัวเลขก็เปลี่ยนตาม N เกิน ~10% ให้รัน backtest ใหม่พร้อมไฟล์ M1 Data ก่อนใช้ผลตัดสินใจ
- ผลเก่าที่รันก่อนระบบ execution realism จะมี — ไม่มี metadata ให้ตรวจ ถ้า model ตัวนั้นยังอยู่ใน shortlist ให้รัน backtest ใหม่เพื่อให้ได้ค่า Realism
ตัวอย่างที่เจอจริง: model เดียวกัน SL/TP แคบ ๆ รันแบบ pessimistic ได้ -53% แต่ optimistic ได้ -21% (ambiguous 27%) — สองตัวเลขนี้มาจาก trade log เดียวกันแท้ ๆ ต่างกันแค่ "การเดา" พอใส่ M1 จริงได้ -38% นี่คือเหตุผลที่ guess N% สูง ๆ ต้องรันใหม่ก่อนเชื่อ ไม่ว่าตัวเลข PF/Return จะสวยแค่ไหน

คอลัมน์ Params: MT5 ใช้ค่าตรงกับตอน train ไหม

เวลา deploy ไป MT5 EA ต้องใช้ feature parameters (เช่น period ของ indicator, spec ของ dataset) ชุดเดียวกับตอน train เป๊ะ — เรียกว่า parameter parity ถ้า MT5 คำนวณ feature ด้วยค่า default ที่ไม่ตรงกับตอน train, observation ที่ส่งเข้า model จะเพี้ยนทั้งเส้น และผลเทรดจริงจะไม่เกี่ยวอะไรกับผล backtest เลย คอลัมน์นี้เช็คให้ว่าหลักฐาน parity อยู่ตรงไหน

✓ sidecar

มีไฟล์ params.json คู่ model

พบ <model>.params.json ใน artifacts — เป็น source of truth ของ parameters ที่ใช้ train export package จะดึงค่าชุดนี้ไปฝังใน config ฝั่ง MT5 ได้ตรงแน่นอน

✓ embedded

ค่าถูกฝังใน config.mqh แล้ว

ไม่มี sidecar แต่ไฟล์ <model>_config.mqh ใน package MT5 มี helper RL_ApplyDataCollectorConfig อยู่ — แปลว่า config ฝั่ง EA มี parameters ฝังไว้ให้ apply เองแล้ว parity ยังโอเค

— defaults

ไม่มีหลักฐาน parity เลย

ไม่เจอทั้ง sidecar และ embedded config — ถ้า deploy ตอนนี้ EA จะใช้ค่า default ซึ่งอาจไม่ตรงกับตอน train ห้าม deploy จนกว่าจะ export package ใหม่ หรือหาไฟล์ params ของ model นั้นเจอ

Equity Curve Viewer และปุ่มทั้ง 4

ใต้ตารางคือ viewer: คลิกแถวไหนในตาราง กราฟ equity ของ model นั้นแสดงทันที (ภาพถูกย่อให้พอดีจอ ~920×360) ใช้เช็คด้วยตาว่า Return ที่เห็นในตารางมีคุณภาพจริงไหม — เส้นไต่เรียบ ๆ กับเส้นที่พุ่งจาก trade เดียวให้ Return เท่ากันได้ แต่คุณค่าไม่เท่ากัน ถ้า model ยังไม่เคย backtest จะขึ้นข้อความ No equity image found... Run backtest first

ปุ่ม ทำอะไร ใช้เมื่อไหร่
Refresh table สแกนไฟล์ trades/artifacts ใหม่ทั้งหมดแล้วสร้างตารางใหม่ หลังรัน backtest / train / export เสร็จ แล้วอยากเห็นผลล่าสุดในตาราง
Open equity image เปิดไฟล์ *_live_bt_equity.png ของแถวที่เลือกด้วยโปรแกรมดูภาพ อยากเห็น equity + drawdown ขนาดเต็ม ซูมดูช่วงที่ DD ลึก
Open HTML chart เปิด *_backtest_chart.html ใน browser — chart interactive ที่ plot จุดเข้า/ออกของทุก trade บนราคา อยาก audit trade รายตัว: เข้าตรงไหน ออกเพราะอะไร ช่วงไหนที่ model พัง
Export report PDF สร้าง pipeline_report_<timestamp>.pdf — หน้าแรกเป็นตารางเปรียบเทียบ (สูงสุด 18 แถว), หน้าสองเป็น equity curve ของแถวที่เลือกอยู่ เก็บ snapshot ผลการทดลอง หรือส่งสรุปให้คนอื่นดูโดยไม่ต้องเปิดโปรแกรม
ทริคเล็ก ๆ: ก่อนกด Export PDF ให้คลิกเลือกแถว model ที่อยากโชว์ equity curve ก่อน — PDF จะใช้กราฟของแถวที่เลือกอยู่ ณ ตอนกด

Artifacts บนดิสก์: ตารางนี้อ่านมาจากไหน

ทุกอย่างที่หน้า Models แสดง มาจากไฟล์จริงใน artifacts/models/<name>/ (ไฟล์ legacy ที่เคยอยู่ root โปรเจกต์ ระบบยังหาเจอและใช้ได้) เข้าใจโครงสร้างนี้แล้วจะ debug ได้เอง เช่น "ทำไม Chart เป็น -" หรือ "ทำไม Params เป็น defaults"

ไฟล์ใน artifacts/models/<name>/ คืออะไร โยงกับหน้า Models ยังไง
<name>.zip ตัว model (PPO policy) ที่ train เสร็จ แค่มีไฟล์นี้ก็ขึ้นในตารางแล้ว (เป็น model only ถ้ายังไม่ backtest)
<name>_norm.csv ค่า normalization ของ feature ตอน train ทุกการ backtest/deploy ต้องใช้ไฟล์นี้คู่กับ zip เสมอ
<name>.params.json parameters ของ dataset/feature ตอน train (sidecar) ต้นทางของค่า ✓ sidecar ในคอลัมน์ Params
<name>.train.json metadata ของรอบ train — รวมผล quick_eval_mc (Monte Carlo ของ quick eval หลัง train) ใช้ย้อนดูว่า model นี้ train ด้วย setting อะไร และ quick eval แข็งแรงแค่ไหน
backtests/<name>_live_bt.meta.json metadata ของ backtest ล่าสุด: settings + result รวมค่า ambiguity/M1 ต้นทางของคอลัมน์ Realism ทั้งคอลัมน์
backtests/<name>_live_bt_trades.csv trade log รายตัวของ backtest ต้นทางของ Trades / Win rate / PF / Return / Max DD (คำนวณสดจากไฟล์นี้)
backtests/<name>_live_bt_equity.png ภาพ equity curve + drawdown สิ่งที่ Equity Viewer และปุ่ม Open equity image แสดง
backtests/<name>_backtest_chart.html chart interactive มีจุดเข้า-ออกทุก trade ทำให้คอลัมน์ Chart เป็น yes และปุ่ม Open HTML chart ใช้ได้

นอกจากนี้ยังมี best/best_model.zip (checkpoint ที่ eval ดีสุดระหว่าง train) และ logs/ (log ระหว่าง train) อยู่ในโฟลเดอร์เดียวกัน

เลือก model ไป deploy: อย่าดูแค่ PF

ตารางเรียงตาม Return และสายตาคนชอบวิ่งไปหา PF สูงสุด — แต่ model ที่ "ตัวเลขสวยสุด" กับ model ที่ "มีหลักฐานแน่นสุด" มักไม่ใช่ตัวเดียวกัน ให้ไล่เช็คตามลำดับนี้ก่อนตัดสิน:

1
Realism

ผลนี้เชื่อได้ไหมตั้งแต่แรก

M1 ✓ หรือ ok = ไปต่อได้; guess N% สูง หรือ - = ตัวเลขทุกช่องในแถวนั้นยังไม่นิ่ง รัน backtest ใหม่พร้อม M1 ก่อนค่อยเทียบ

2
Sample

Trades มากพอไหม

PF 3.0 จาก 12 trades แพ้ PF 1.5 จาก 300 trades เกือบทุกกรณี — trades น้อยหมายถึงตัวเลขทุกตัวมี noise สูง และ PF = inf คือธงแดง ไม่ใช่ธงเขียว

3
Significance

เปิด backtest report ดู MC / significance

ตารางนี้เป็นแค่หน้าสรุป — ก่อน deploy ให้กลับไปดูผลเต็มของ backtest รอบนั้น: random baseline (model ชนะ agent สุ่ม ≥ 95% ไหม) และ Monte Carlo shuffle (worst-case DD กับ P(hard stop) รับได้ไหม) รวมถึง quick_eval_mc ใน train.json

4
Parity + Curve

เช็ค Params และ equity curve ปิดท้าย

Params ต้องเป็น ✓ sidecar หรือ ✓ embedded (ห้าม deploy ตัวที่เป็น — defaults) และ equity curve ต้องกำไรกระจายหลาย trade หลายช่วงเวลา ไม่ใช่พุ่งครั้งเดียว

สถานะ เงื่อนไข ตัดสินใจ
Deploy candidate live backtest + Realism M1 ✓/ok + trades มากพอ + ผ่าน MC/baseline + Params ✓ + curve สุขภาพดี ไป Walk-Forward / export package ต่อได้
Re-verify ตัวเลขดีแต่ Realism เป็น guess N% หรือ -, หรือมีแต่ผล env backtest รัน live backtest ใหม่พร้อม M1 ก่อน แล้วค่อยกลับมาเทียบ
Not ready model only, trades น้อยมาก, PF < 1, หรือ Params — defaults ยังไม่มีสิทธิ์เข้ารอบ — กลับไป backtest/แก้ params ก่อน
ประโยคสอน user: ตาราง Models คือกระดานคะแนน ไม่ใช่กรรมการตัดสิน — มันบอกว่า "ตัวไหนน่าไปดูต่อ" แต่การตัดสิน deploy ต้องอ่านหลักฐานเต็ม (Realism, MC, significance, parity) ของตัวนั้นเสมอ

Gotcha ที่เจอบ่อยในหน้านี้

Overwrite

ตั้งชื่อ model ซ้ำ = ทับ artifacts เดิม

ทุกไฟล์ผูกกับชื่อ model — ถ้า train ใหม่ด้วยชื่อเดิม zip, norm, params, train.json และผล backtest ทั้งหมดใน artifacts/models/<name>/ จะถูกเขียนทับ ผลเก่าหายถาวรโดยไม่มีคำเตือน

วิธีป้องกัน: ใส่ version ต่อท้ายชื่อเสมอ เช่น rl_uj_h4_v1, rl_uj_h4_v2 — ได้ประโยชน์สองต่อ: ผลเก่าไม่หาย และทุก version โผล่เทียบกันในตารางนี้เอง

ตัวเลขในแถวคือ "ผลล่าสุด" ไม่ใช่ "ผลดีสุด"

ถ้ารัน backtest ซ้ำหลายรอบด้วย setting ต่างกัน แถวในตารางแสดงเฉพาะรอบล่าสุด — เช่น รอบแรก confidence 0 ได้ PF 1.6 แล้วรอบสอง confidence 0.85 ได้ PF 0.9 ตารางจะโชว์ 0.9 อยากเก็บผลหลาย setting ให้จด/Export PDF ไว้ก่อนรันทับ

เช็คเร็วก่อน train ชื่อใหม่: เปิดหน้า Models ดูก่อนว่าชื่อที่จะใช้ มีอยู่ในตารางแล้วหรือยัง — เห็นชื่อซ้ำเมื่อไหร่ เปลี่ยน version ทันที
