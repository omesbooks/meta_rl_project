Flow Step 2 · Regime Check

Regime Check — จัด train data ให้อยู่โลกเดียวกับตลาดปัจจุบัน

บทนี้อธิบายหน้า Regime Check: ทำไม regime shift ทำให้โมเดลที่ train ผ่านกลับขาดทุนหนักตอน test, วิธีเลือก detection method (HMM / K-Means / PELT), การใช้ Gemini ตั้งชื่อ event อัตโนมัติ, การอ่านตาราง breakpoints และปุ่ม Use Selected as Train Cutoff ที่ตัดข้อมูลให้ตรง regime ปัจจุบันในคลิกเดียว

ทำไม Regime สำคัญ เคสจริง -38.7% ขั้นตอนใช้งาน 3 Methods Parameters Gemini Events อ่านตาราง Breakpoints Train Cutoff Trade-off

Regime คืออะไร และทำไมต้องเช็คก่อน Train

Regime คือ "สภาพตลาด" ช่วงหนึ่ง ๆ ที่ราคามีพฤติกรรมทางสถิติแบบเดียวกัน เช่น mean, volatility, แนวโน้มหลัก. เหตุการณ์ใหญ่อย่าง Brexit, COVID, วิกฤต Lehman ทำให้ตลาด "ย้ายโลก" — distribution ของราคาเปลี่ยนไปถาวร ไม่ใช่แค่ผันผวนชั่วคราว

Problem

โมเดลเรียนจากโลกเก่า

ถ้า train data คลุมหลาย regime โมเดล RL จะเรียนกฎของโลกเก่าไปด้วย เช่น "ราคาต่ำกว่า mean เดี๋ยวก็เด้งกลับ" ทั้งที่โลกใหม่ mean ย้ายไปแล้ว

Evidence

Train ดี Test พัง = สัญญาณ regime drift

อาการคลาสสิก: eval reward ตอน train ดูดี แต่ backtest บนช่วงปัจจุบันขาดทุนซ้ำ ๆ ยิ่ง train นาน ยิ่งแย่ลง เพราะโมเดลยิ่งจำโลกเก่าแม่นขึ้น

Fix

ตัด train data ให้อยู่ regime เดียวกับปัจจุบัน

หา breakpoint ที่ตลาดเปลี่ยนโลกครั้งล่าสุด แล้วตัดข้อมูลก่อนหน้านั้นทิ้ง ให้ train และ test อยู่ใน distribution เดียวกัน — นี่คือหน้าที่ของหน้า Regime Check

ประโยคสอน user: โมเดลไม่ได้โง่ มันแค่เรียนมาจากโลกที่ไม่มีอยู่แล้ว ก่อนโทษ hyperparameter ให้เช็คก่อนว่า train data กับตลาดปัจจุบันอยู่โลกเดียวกันหรือเปล่า

เคสจริง: GBPUSD ขาดทุน -38.7% เพราะ regime shift

เคสนี้เกิดจริงระหว่างพัฒนาระบบ และเป็นเหตุผลที่หน้านี้ถูกสร้างขึ้นมา ใช้เล่าให้ user ฟังก่อนสอนปุ่มต่าง ๆ เพราะมันตอบคำถาม "ทำไมต้องมีหน้านี้" ได้ชัดที่สุด

ช่วงข้อมูล บทบาท ราคาเฉลี่ย GBPUSD ผลที่เกิด
2004 – 2022 Train (full history) ~1.55 โมเดลเรียนว่า "ราคาปกติ" อยู่แถว 1.55
2022 – ปัจจุบัน Test ~1.27 ราคาย้าย regime ไปแล้ว (~18% shift)
ผลลัพธ์รวม โมเดลกด BUY ซ้ำ ๆ รอราคากลับ mean เก่า → return -38.7%
สิ่งที่โมเดลคิด

"1.27 ถูกมาก เดี๋ยวเด้งกลับ 1.55"

โมเดลเห็นราคาปัจจุบันต่ำกว่า mean ที่เรียนมาตลอด 18 ปี จึงกด BUY แล้วถือรอ mean reversion ที่ไม่มีวันมา ยิ่งรันนานยิ่งขาดทุนสะสม (-26.9% แล้วแย่ลงเป็น -38.7%)

สิ่งที่แก้จริง

ตัด train data เหลือหลัง Brexit

HMM ชี้ breakpoint ใหญ่ที่ Brexit 2016 และ COVID 2020 การ retrain บน subset หลัง Brexit ทำให้ train distribution ตรงกับ test — distribution shift หายไปโดยไม่ต้องแตะโมเดลเลย

ข้อคิดสำคัญ: ปัญหานี้แก้ด้วยการปรับ learning rate, เพิ่ม steps, เปลี่ยน reward ไม่ได้เลย เพราะต้นเหตุอยู่ที่ ข้อมูล ไม่ใช่ตัวโมเดล — data quality ชนะ model tuning เสมอ

ขั้นตอนใช้งานหน้า Regime Check

Flow แนะนำสำหรับใช้จริง: เริ่มจากไฟล์ dataset ที่จะเอาไป train แล้วจบที่ไฟล์ใหม่ที่ตัดแล้วพร้อม train ทันที

1
Data

Browse เลือก CSV

เลือกไฟล์ dataset ที่จะใช้ train (ต้องมีคอลัมน์ timestamp และ close) GUI จะโชว์จำนวน rows และช่วงวันที่ให้ตรวจว่าใช่ไฟล์ที่ตั้งใจ

2
Events

Refresh events with Gemini (ครั้งแรกของ symbol ใหม่)

กดปุ่ม 🤖 Refresh events with Gemini ให้ระบบหา price shock ใหญ่ ๆ แล้วให้ AI ตั้งชื่อ event ให้อัตโนมัติ — ทำครั้งเดียวต่อ symbol ก็พอ ผลถูกเก็บใน known_events.json ใช้ซ้ำได้ทุกรอบ

3
Detect

เลือก HMM แล้ว Run Detection

เริ่มจาก HMM 3-state ⭐ (default) เพราะให้ผลดีสุดจากการทดสอบ รันเสร็จใน ~3 วินาที ตาราง breakpoints จะขึ้นเองอัตโนมัติ และเปิด chart ดูเส้น breakpoint บนกราฟราคาได้จากปุ่ม 📄 Open Chart

4
Pick

เลือก breakpoint ใหญ่สุดที่ใกล้ปัจจุบัน

มองหาแถวที่ match กับ event ใหญ่ (✓ Brexit, ✓ COVID) และเป็นการเปลี่ยนโลกครั้งล่าสุด ที่ยังเหลือข้อมูลหลังจากนั้นมากพอสำหรับ train

5
Cutoff

Use Selected as Train Cutoff

กดปุ่มเดียว ระบบจะตัด CSV, copy .params.json sidecar แล้วพาไปหน้า Train พร้อมไฟล์ใหม่ที่เลือกให้แล้ว

6
Verify

Retrain แล้วเทียบผลกับโมเดลเดิม

Train บน subset ใหม่ แล้ว backtest เทียบกับโมเดล full-history ถ้า regime drift คือต้นเหตุจริง ผลบนช่วง test ปัจจุบันควรดีขึ้นชัดเจน

3 Detection Methods: เลือกตัวไหน

เบื้องหลังหน้านี้คือ regime_compare.py ซึ่งตอนวิจัยทดสอบมา 6 วิธี แล้วคัดเหลือ 3 วิธีที่คุ้มค่าให้เลือกใน GUI — คะแนน "จับ events" วัดจากการเจอ breakpoint ภายใน ±90 วันของ event จริง (Lehman / Brexit / Truss) บนข้อมูล GBPUSD H4

Method หลักการ จับ Events ความเร็ว เหมาะกับ
HMM 3-state ⭐ Hidden Markov Model มอง [log return, rolling volatility] แล้วแบ่งตลาดเป็น 3 hidden state (เช่น bull/bear/sideways) — breakpoint คือจุดที่ state เปลี่ยนแล้วอยู่ยาว 3/3 ~3s ค่า default — ใช้ตัวนี้ก่อนเสมอ
K-Means rolling Cluster บน rolling features [mean, std, slope] — วันที่ label cluster เปลี่ยนแล้วคงอยู่ = breakpoint 2/3 เร็วสุด ~60ms สแกนเร็ว ๆ หรือ cross-check ผล HMM
PELT (changepoint) Optimal segmentation ด้วย RBF kernel (library ruptures) — หาจุดตัดที่แบ่ง series ได้ดีที่สุดทางคณิตศาสตร์ 2/3 ช้า ~3 นาที ยืนยันผลรอบสุดท้าย เมื่อยอมรอได้
ทำไม HMM ชนะ

มองทั้ง return และ volatility พร้อมกัน

Regime shift จริงมักมาคู่กัน: ราคาย้าย mean และ volatility เปลี่ยน HMM เห็น joint distribution ของทั้งสองตัว จึงแยก "โลกเปลี่ยน" ออกจาก "แค่ผันผวน" ได้ดีกว่า

กันสัญญาณหลอก

Persistence filter 30 วัน

ทั้ง HMM และ K-Means กรอง breakpoint ที่ state เด้งกลับเร็ว: ต้องอยู่ state ใหม่อย่างน้อย 25 จาก 30 วันถัดไปถึงนับเป็น breakpoint จริง (no flapping) — เส้นที่เห็นในตารางจึงเป็นการย้ายโลกจริง ไม่ใช่ noise

หมายเหตุ

ทุกวิธีวิเคราะห์บน daily

ระบบ resample H4 → daily close ก่อนวิเคราะห์เสมอ เพื่อความเร็วและลด noise แต่ตอนตัด cutoff จริงจะตัดบนไฟล์ H4 ต้นฉบับเต็ม ๆ ไม่ใช่ไฟล์ daily

Parameters ของแต่ละ Method

แต่ละ method มี parameter ชุดเดียวที่ต้องรู้ — GUI จะโชว์เฉพาะช่องของ method ที่เลือกอยู่ ค่า default ผ่านการทดสอบมาแล้ว ส่วนใหญ่ไม่ต้องแตะ

Method Parameter ความหมาย คำแนะนำ
HMM States (default 3) จำนวน hidden state ที่ให้โมเดลแบ่งตลาด (3 = bull/bear/sideways) ใช้ 3 เป็นหลัก; เพิ่มเป็น 4-5 เฉพาะเมื่ออยากแยก regime ละเอียดขึ้น แต่ breakpoint จะถี่ขึ้นตาม
K-Means Clusters k (default 3) จำนวนกลุ่มสภาพตลาด ตีความเหมือน HMM states — เริ่มที่ 3
Window (default 60 วัน) ความยาว rolling window ที่ใช้คำนวณ [mean, std, slope] window สั้น = ไวต่อการเปลี่ยนแปลงแต่ noise เยอะ; window ยาว = นิ่งแต่เจอ breakpoint ช้า
PELT Penalty (default 50) ต้นทุนของการเพิ่ม breakpoint หนึ่งจุดใน optimization สูง = ตัด break น้อย จับเฉพาะ shift ใหญ่ ๆ; ต่ำ = ตัดถี่ เจอ break ยิบย่อยเยอะ
หลักการสอน: อย่าจูน parameter เพื่อ "ให้เจอ breakpoint ที่อยากเห็น" — ให้รัน default ก่อน แล้วถ้าผลขัดกับสายตา ค่อยลองอีก method มา cross-check ว่า breakpoint นั้นเจอเหมือนกันไหม

Gemini Auto-Events: ให้ AI ตั้งชื่อเหตุการณ์ให้

ตาราง breakpoints จะอ่านง่ายขึ้นมากถ้ารู้ว่าแต่ละจุด "คือเหตุการณ์อะไร" แทนที่จะต้องนั่งหาเองว่าวันนั้นเกิดอะไรขึ้น ปุ่ม 🤖 Refresh events with Gemini ทำงานเป็น pipeline อัตโนมัติผ่าน gemini_labeler.py:

1
Detect

หา Top-K price shocks จาก CSV

ระบบหา "วันช็อค" — วันที่ |return| ผิดปกติเทียบ rolling baseline 60 วัน (z-score) เลือก Top-K ตัวที่ z สูงสุดก่อน (default 15) โดยเว้นระยะขั้นต่ำ 30 วัน ไม่ให้ event เดียวกันกินหลาย slot

2
Label

ถาม Gemini ว่าแต่ละวันเกิดอะไรขึ้น

ส่งคำถามทีละวัน เช่น "วันที่ X GBPUSD ร่วง 3.2% ในวันเดียว เกิดจากเหตุการณ์อะไร" Gemini ตอบชื่อ event + category + confidence กลับมาเป็น JSON (ระบบเว้น 4.5 วินาทีต่อ call เพื่อไม่ชน rate limit free tier 15 req/min)

3
Save

บันทึกลง known_events.json

ผลถูกเก็บเป็นไฟล์ known_events.json ที่ regime detection ทุกรอบหลังจากนั้น โหลดมาใช้ match อัตโนมัติ — สถานะไฟล์ (จำนวน events, symbol, last updated) โชว์อยู่ใต้ปุ่มตลอด

เรื่องต้องรู้ รายละเอียด
ต้องมี API key ใช้ Gemini free tier ได้ — ขอ key ฟรีที่ aistudio.google.com แล้วใส่ในหน้า Settings ก่อนกดปุ่ม (ระบบเก็บใน api_keys.json ที่ gitignore ไว้ ไม่หลุดขึ้น repo)
ไม่มี key ก็รันได้ จะได้เฉพาะวันที่ shock โดยไม่มีชื่อ (label เป็น Shock @ YYYY-MM) — ยังใช้ match ได้ แต่อ่านยากกว่า
ไม่เคยรันเลยก็ไม่พัง ถ้ายังไม่มี known_events.json ระบบ fallback ไปใช้ 3 events ที่ hardcode ไว้ (Lehman / Brexit / Truss) ซึ่งเหมาะกับ GBPUSD เท่านั้น — symbol อื่นควร refresh ก่อน
Symbol / Top-K ใส่ symbol ให้ตรงไฟล์ (Gemini ใช้เป็น context ตอนเดาเหตุการณ์) และ Top-K คือจำนวน shock สูงสุดที่จะ label (default 15 ≈ ใช้เวลา ~1 นาที)
จุดที่คนเข้าใจผิดบ่อยที่สุด: events เป็นแค่ "ป้ายชื่อ" สำหรับ validate และอ่านผลง่ายเท่านั้น — ไม่มีผลใด ๆ ต่อการหา breakpoint. HMM/K-Means/PELT หา breakpoint จากราคาล้วน ๆ แล้วค่อยเอา events มาทาบทีหลังว่าจุดไหนตรงกับเหตุการณ์จริงบ้าง ดังนั้นถึง Gemini จะ label ผิดหรือไม่มี key ผล detection ก็ไม่เปลี่ยนแม้แต่จุดเดียว

อ่านตาราง Detected Breakpoints

หลังรัน detection เสร็จ ตารางจะถูกเติมอัตโนมัติจาก regime_single_data.json แต่ละแถวคือ breakpoint หนึ่งจุด พร้อมข้อมูลว่า match กับ event ที่รู้จักหรือไม่

คอลัมน์ ความหมาย วิธีใช้
Breakpoint Date วันที่ algorithm ตรวจพบว่าตลาดเปลี่ยน regime วันนี้คือ candidate สำหรับ train cutoff — ข้อมูลตั้งแต่วันนี้เป็นต้นไปถือว่าอยู่โลกใหม่
Known Event Match ✓ ชื่อ event ถ้ามี event ที่รู้จักภายใน ±90 วัน, — ถ้าไม่มี แถวที่มี ✓ น่าเชื่อกว่า เพราะมีเหตุการณ์จริงในโลกรองรับว่าทำไมตลาดถึงเปลี่ยน
Days Apart ระยะห่างระหว่าง breakpoint กับ event จริง (วัน) ยิ่งน้อยยิ่งแม่น — หลักหน่วยถึงหลักสิบวันคือปกติ เพราะตลาดมักเริ่มขยับก่อน/หลังข่าวเล็กน้อย

เหนือตารางมี summary line สรุปผลรวมของรอบนั้น อ่านแบบนี้:

  • Method: HMM · 6 breakpoints · 4/15 known events matched · 5,432 bars analyzed in 2.87s
  • จำนวน breakpoints — เยอะเกิน (10+) แปลว่า method/param ไวไป, น้อยเกิน (0-1) แปลว่าหยาบไป
  • score matched — สัดส่วน events ที่ detection จับได้ ใช้เป็น sanity check ว่าวิธีนี้ "เห็น" เหตุการณ์จริงบ้างไหม (ตัวหารคือจำนวน events ทั้งหมดใน known_events.json ไม่ใช่ 3 เสมอไป)
  • สีเขียว = match ratio ดี (≥40%), สีเหลือง = ต่ำ ควร cross-check ด้วย method อื่น
เลือกแถวไหนไปเป็น cutoff: หลักคิดคือ "การย้ายโลกครั้งใหญ่ครั้งล่าสุด ที่ยังเหลือข้อมูลพอ train" — breakpoint ที่มี ✓ event ใหญ่ (Brexit, COVID) และใกล้ปัจจุบันที่สุด โดยหลัง cutoff ควรเหลือข้อมูลอย่างน้อยหลายพัน bars (ดู section Trade-off ด้านล่าง)

Use Selected as Train Cutoff: ปุ่มปิดจ็อบ

นี่คือ killer feature ของหน้านี้ — เปลี่ยนผลวิเคราะห์เป็นไฟล์ train จริงในคลิกเดียว เลือกแถว breakpoint ในตาราง แล้วกด 🎯 Use Selected as Train Cutoff ระบบจะทำให้ครบทุกอย่าง:

1
Filter

ตัด CSV เหลือเฉพาะหลัง cutoff

กรองแถวที่ timestamp >= วันที่เลือก จากไฟล์ H4 ต้นฉบับ แล้วบันทึกเป็นไฟล์ใหม่ชื่อ <ชื่อเดิม>_from_<YYYY-MM-DD>.csv (ไฟล์แม่ไม่ถูกแตะ) — log จะบอกว่าเหลือกี่แถวจากทั้งหมด

2
Sidecar

Copy .params.json ตามไปด้วย

ระบบ copy <ชื่อเดิม>.params.json ไปเป็นของไฟล์ใหม่อัตโนมัติ feature config / parity settings จึงติดไปครบ ไม่ต้อง Attach เองที่หน้า Train

3
Jump

เด้งไปหน้า Train พร้อมไฟล์ใหม่

หน้าจอสลับไปหน้า Train โดยไฟล์ _from_<date> ถูกเลือกไว้ให้แล้ว ตั้งชื่อ model ใหม่แล้วกด train ได้ทันที

ประโยคสอน user: cutoff ไม่ใช่การลบข้อมูล — ไฟล์เต็มยังอยู่เหมือนเดิม เราแค่สร้าง "เวอร์ชันโลกปัจจุบัน" แยกออกมาอีกไฟล์ ถ้าผล train ไม่ดีขึ้นก็กลับไปใช้ไฟล์เต็มหรือลอง cutoff จุดอื่นได้เสมอ

Trade-off: ตัดข้อมูล = ข้อมูลน้อยลง

การ cutoff ไม่ใช่ของฟรี — ทุกครั้งที่ตัด เราแลก "regime ตรงขึ้น" กับ "จำนวนข้อมูลที่ลดลง" ต้องชั่งสองข้างนี้ทุกครั้ง:

ได้อะไร

Distribution ตรงกับตลาดจริง

โมเดลเรียนเฉพาะกฎของโลกปัจจุบัน ไม่ลาก bias จาก regime เก่ามาปน train/test อยู่ distribution เดียวกัน ผล eval สะท้อนของจริงมากขึ้น

เสียอะไร

Sample น้อยลง เสี่ยง overfit ขึ้น

RL ต้องการข้อมูลเยอะ ถ้าตัดจนเหลือปีสองปี โมเดลอาจจำ pattern เฉพาะช่วงแทนที่จะเรียนกฎทั่วไป และเหตุการณ์หายาก (crisis, flash crash) อาจไม่เหลือให้เรียนเลย

สถานการณ์ สัญญาณ ตัดสินใจ
ควรตัด Train ดี test พัง + HMM เจอ breakpoint ใหญ่ชัดเจน + หลัง cutoff ยังเหลือข้อมูลหลายพัน bars Cutoff แล้ว retrain เทียบผล — เคส GBPUSD post-Brexit คือแบบนี้
ชั่งใจ Breakpoint ล่าสุดใกล้ปัจจุบันมากจนหลัง cutoff เหลือข้อมูลน้อย ลองถอยไปใช้ breakpoint ใหญ่ก่อนหน้า หรือใช้ไฟล์ตัดแล้ว fine-tune แทน train ใหม่จากศูนย์
อย่าเพิ่งตัด ผล backtest แย่แต่ breakpoint ที่เจอเบา ๆ ไม่ match event อะไรเลย / method อื่นไม่เจอซ้ำ ปัญหาอาจไม่ใช่ regime — กลับไปดู Quality Check, feature, reward ก่อน
กติกาสุดท้าย: cutoff เป็นสมมติฐาน ไม่ใช่คำตอบ — ต้องพิสูจน์ด้วยการ retrain แล้ว backtest เทียบกับโมเดลเดิมบนช่วง test เดียวกันเสมอ ถ้าผลไม่ดีขึ้น อย่าฝืนตัดลึกลงเรื่อย ๆ ให้กลับไปตั้งคำถามว่าต้นเหตุคืออะไรกันแน่
